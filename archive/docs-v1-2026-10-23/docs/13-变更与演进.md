# 13 · 变更与演进

[返回总览](00-总览与索引.md)

## 变更类型

| 类型 | 前置条件 | 需要 ADR | 门禁 |
|---|---|---|---|
| 修 bug | 先写失败用例 | 否 | 全部 |
| 加功能 | 对应需求编号 | 涉及接口或结构时 | 全部 |
| 重构 | 行为不变，测试护航 | 跨模块时 | 全部 |
| 结构变更 | 影响面清单与分期方案 | 是 | 全部 |
| 紧急修复 | 先止血，后补证 | 否 | 24 小时内补齐 |

## 完成定义

一项改动同时满足以下七条，才算完成：

1. 需求可追溯：对应 [01](01-需求与边界.md) 的编号，或说明属于维护。
2. 行为有测试：新增或修改的行为有用例，修 bug 有用例先红后绿。
3. 门禁全过：[12](12-测试与质量门禁.md) 的六条命令全部通过。
4. 文档同步：按下方矩阵修改对应文档。
5. 证据留存：运行与判定有截图、日志或数据可查。
6. 回滚清晰：说明出问题时怎么退回上一个可用状态。
7. 评审清单通过。

## 评审清单

每次改动逐条自查，任何一条为否都要说明理由：

- [ ] 依赖方向是否被违反。
- [ ] 有没有把流程写进代码。
- [ ] 有没有出现第二个真源。
- [ ] 失败路径是否有明确处置，是否计入预算。
- [ ] 是否打印了敏感信息。
- [ ] 是否引入了无超时的外部调用。
- [ ] 新增配置项是否有类型、默认值、范围与说明。
- [ ] 测试是否覆盖失败路径，而不只是成功路径。
- [ ] 文档与代码是否一致。
- [ ] 是否留下绕行而没有登记债务。

## 架构决策记录

满足以下三条之一时写 ADR，放在 `docs/adr/`：

1. 难回退：改动成本高，事后修改代价大。
2. 反直觉：后来的人会问「为什么这么做」。
3. 有取舍：存在真实替代方案，且选择有明确理由。

ADR 格式：状态、日期、背景、决策、后果、替代方案。

## 版本与兼容

- 项目处于 0.x，接口可以调整，但每次调整要在 [03](03-数据模型与接口.md) 同步，并在提交说明里写明影响。
- 配置项删除或改名，要提供迁移：读到旧键时提示新键，并继续生效一个版本。
- 对外 API 一旦有第二个使用方，按版本号管理，不静默破坏。

## 弃用

1. 标记：代码注释写明替代方案与预期移除时间。
2. 告警：运行日志输出一次弃用提示。
3. 移除：一个版本后删除，历史进提交说明。

## 技术债台账

所有绕行、欠测试、欠重构的项记在 `DEBT.md`。

| 字段 | 要求 |
|---|---|
| 编号 | `D-001` 递增 |
| 日期 | 记账时间 |
| 债务 | 一句话说清欠了什么 |
| 原因 | 为什么当时欠下 |
| 影响 | 不还会怎样 |
| 归还期限 | 具体日期或版本 |
| 状态 | 未还 / 部分还 / 已还 |

规则：

- 同时未还的债务不超过 20 笔；超过先还债再加功能。
- 每月复审一次，逾期的在周报里单独列出。
- 已还的条目删除，记录进提交说明。

## 事故复盘

真实事故写进 `docs/incidents/<日期>-<简述>.md`：

1. 时间线：发生了什么，什么时候。
2. 影响：哪次运行、什么结论、用户看到什么。
3. 根因：直接原因与深层原因。
4. 回归用例：补了哪条测试。
5. 规矩更新：是否需要改宪法、门禁或评审清单。

## 阶段体检

| 周期 | 做什么 |
|---|---|
| 每月 | 跑一次架构体检与技术债盘点，更新 `DEBT.md` 与 ADR |
| 每季度 | 全量回归、性能基线复测、废弃代码清理、文档与代码一致性抽查 |

体检发现的问题进入 `TASKS.md`，不口头记。
