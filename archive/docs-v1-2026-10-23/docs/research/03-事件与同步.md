# 03 · 事件与同步

[返回调研总览](00-dsh-mobile-调研总览.md)

## 结论

dsh-mobile 的实时层可以概括成四句话：先给原子快照，再按单调序号给增量；历史分页与实时尾部按序号合并，实时覆盖同序号；序号断档或格式版本不符时停止增量、重建基线；坏事件不推进状态，宁可停更也不让两端状态分叉。

lap-backstop 的 HTTP + SSE 可以直接采用这四条，不需要 KMP 或 MVI。

## 单向数据流

dsh-mobile 的 shared 层是唯一业务状态源：

```text
UI Intent → Store/Reducer（唯一状态）→ 有序 Event（state patch + effects）
        → 平台校验 → UI 镜像 / 执行副作用
```

平台不跑第二套 Reducer，只校验事件、重建可重建的 UI 状态。校验失败时该域适配器永久停更，避免两端状态分叉。

映射到 lap-backstop：

```text
运行线程（单写者）→ SQLite run_events（分配 seq）
        → SSE 广播（只读）→ Android 客户端状态
用户操作 → HTTP POST → 校验 → 写入配置或发出命令 → 新事件
```

运行中的快照只由运行线程写；界面修改走 HTTP 落到配置层，不直接改运行中的快照。这与现有「运行期配置冻结」一致。

## 事件信封

建议每个事件统一为：

```json
{
  "id": 1024,
  "type": "step.finished",
  "run_id": "run-20261019-001",
  "at": "2026-10-19T01:02:03+08:00",
  "schema_version": 1,
  "payload": { "step_id": "wait_login", "status": "ok", "elapsed_ms": 4210 }
}
```

- `id` 就是 `run_events.seq`，单调递增，直接作为 SSE 的 `id:` 字段。
- `type` 是稳定事件名，不让客户端解析 `payload` 猜类型。
- `schema_version` 跟 `/api/health` 返回的版本一起校验；不匹配时客户端停止增量并重取快照。
- `payload` 只放本次变化需要的字段；全量状态走快照接口。

SSE 帧形状：

```text
id: 1024
event: step.finished
data: {"type":"step.finished","run_id":"...","at":"...","schema_version":1,"payload":{...}}

```

服务端可给 `retry: 3000` 建议重连间隔。

## 快照与增量

### 快照

`GET /api/status` 返回当前全量状态，至少包含：

| 字段 | 内容 |
|---|---|
| `seq` | 快照对应的最新事件序号 |
| `server_time` | 服务端时间，用于客户端对齐 |
| `run` | 当前运行：id、编排、步骤、开始时间、状态 |
| `queue` | 排队中的运行 |
| `last_conclusion` | 最近一次结论：完成 / 未完成 / 判不出 |
| `pending` | 待处理事项：冲突、失败、判不出、需要确认的操作 |
| `capabilities` | 能力位，例如 `sse-v1`、`snapshot-v1`、`conflict-resolve-v1` |

客户端状态 = 快照 + `seq` 之后的增量。任何时刻都能用一次快照重建，不依赖本地缓存。

### 增量

- 只推变化：`step.started`、`step.finished`、`evidence`、`judgement`、`conflict.detected`、`alert`、`run.finished` 等。
- 同一序号以最新记录为准；`upsert` 用于修正同序号记录，`replace` 用于基线重建。
- 客户端按 `id` 去重；收到不大于当前水位的 `id` 直接丢弃。

### 断档与重建

```text
连接 → 带 since_seq 订阅 → 正常增量
  ├─ 收到 gap（游标过旧/保留窗口已过）→ GET /api/status 取快照 → 用新 seq 重新订阅
  ├─ 断线 → 退避重连 → 带 Last-Event-ID → 服务端补发 → 若补不齐则 gap
  └─ schema_version 不符 → 清本地状态 → 取快照 → 重新订阅
```

服务端保留窗口建议与运行记录保留期一致；超出窗口的 `since_seq` 返回 `gap`，不要静默从中间开始推，否则客户端会缺一段状态。

### 慢消费者

- 每个 SSE 连接一个有界缓冲；写不进去就断开该连接并记录，让客户端重连后取快照。
- 不无限堆积，也不把慢消费者拖垮整个服务。

## 历史分页与实时尾部合并

- 历史接口：`GET /api/runs/{id}/events?before_seq=...&limit=60`，返回 `{events, has_more, next_before_seq}`。
- `next_before_seq` 指向更早一页的起点；同批出现重复游标判失败，`has_more` 却没有新游标也判失败，避免死循环。
- 客户端合并规则：先放分页结果，再放实时尾部；按 `seq` 建表，实时覆盖同序号；最后按 `seq` 排序。
- 晚到的历史页不能覆盖已经收到的最终消息或增量。
- 分页游标与 `schema_version` 成对使用；格式升级后旧游标作废。

## 流式去重

如果 AI 归因或公告解读逐字推送，可以借用 dsh-mobile 的连续性校验：

| 字段 | 作用 |
|---|---|
| `attempt_id` | 一次生成尝试的标识；切换尝试即清空临时内容 |
| `revision` | 每次增量严格 +1；断档即重订阅 |
| `index` | 同一 revision 内的分片序号，必须连续 |
| `cursor` | 已提交的持久事件水位 |

最终消息必须能对应到一条持久事件；对不上就判定结算缺失并重建，不让临时流与最终记录同时存在。

lap-backstop 如果没有逐字流，只保留 `seq` 级去重即可，不必引入 attempt/revision。

## 断线恢复

| 阶段 | 行为 |
|---|---|
| 断线 | 保留当前快照与已见 `seq`；停止增量；界面显示「重连中」 |
| 退避 | 2 秒起，指数退避，封顶 30 秒；恢复后回到「在线」 |
| 重连 | 带 `Last-Event-ID` 或 `since_seq` 订阅；服务端补发 |
| 补不齐 | 收到 `gap` 或版本不符 → 取 `/api/status` → 用新 `seq` 重新订阅 |
| 写操作 | 重连中与离线时禁用「叫停」「冲突处理」等写操作，并给出原因；不做本地排队重放 |

退避不是越短越好：手机锁屏、切后台、路由器 NAT 都会让连接静默失效；固定高频重连会耗电，也会在服务端制造无效连接。

## fail-closed 清单

| 场景 | 行为 |
|---|---|
| 事件 JSON 解码失败 | 不推进状态，记录脱敏摘要，等待下一次快照 |
| 序号断档 | 停止增量，取快照重建 |
| `schema_version` 不符 | 清缓存，取快照，按新版本订阅 |
| 快照与增量同序号冲突 | 以快照或最新增量为准，不能两份都保留 |
| 历史页跨运行或跨会话 | 拒绝整页，不合并 |
| 分页游标重复或缺失 | 停止加载，报错，不静默循环 |
| SSE 缓冲溢出 | 断开连接，让客户端重连取快照 |
| 写操作重复提交 | 服务端用请求 ID 幂等或忙拒绝，不重复执行 |

## 对 lap-backstop 的落点

### docs/02

- 在「数据流」后补「状态与实时层」：配置（可编辑）、运行快照（可重建）、事件日志（`run_events`，唯一序号来源）三份状态。
- 写明单写者：运行线程写状态并分配 `seq`；SSE 广播只读；界面写入走 HTTP 落到配置层。
- 失败隔离表补两行：SSE 缓冲溢出、事件序号断档。

### docs/03

- SSE 事件表补 `id`、`type`、`run_id`、`at`、`schema_version`、`payload`；补 `snapshot` 与 `gap` 两种事件。
- `/api/runs/{id}/events` 增加 `before_seq`、`limit`、`has_more`、`next_before_seq`；全局 `/api/events` 增加 `since_seq`。
- `/api/health` 增加 `version`、`capabilities`、`server_time`。
- 错误码补 `E_STREAM_GAP`、`E_TOKEN_REVOKED`。

### docs/06

- 「实时」节写成可执行顺序：连接 → 带 `since_seq` 订阅 → 断线 → 重取快照 → 再订阅；客户端按 `seq` 去重。
- 页面状态补「在线 / 重连中 / 离线」三态；离线和重连中禁用写操作。
- 叫停与冲突处理改成「请求-确认」：发出后显示进行中，服务端拒绝时保持原状，不乐观改成已停止/已处理。
