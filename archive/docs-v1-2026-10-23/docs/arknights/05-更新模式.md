# 05 · 更新模式

## 目标

大版本更新日先完成客户端更新，再把当天日常补上；更新失败或超时，停手通知并顺延。

## 数据源

| 源 | 地址 | 用途 |
|---|---|---|
| 官网公告列表 | `https://ak.hypergryph.com/api/news?page=1&pageSize=20` | 标题、时间、链接 |
| 公告正文 | `https://ak.hypergryph.com/news/<cid>` | 维护时间窗、更新类型 |
| 官方版本接口 | `https://ak-conf.hypergryph.com/config/prod/official/Android/version` | `clientVersion`、`resVersion` |
| 游戏内公告 | 安卓无障碍树读取 | 补充签到类活动信息 |

抓取规则：

- 白天每 6 小时拉一次列表；正文按需拉取并缓存。
- 请求带浏览器 UA，不经过系统代理。
- 抓取失败沿用上次结果并标记 `stale`，不凭猜测断言。

## 解析

从标题与正文提取：

| 字段 | 示例 |
|---|---|
| 更新类型 | 停机维护、闪断更新 |
| 时间窗 | `2026年09月20日16:00 ~ 16:10` |
| 版本号 | `clientVersion` 由 2.4.01 变为 2.5.00 |

标题与正文的常见写法都要覆盖：

```text
[明日方舟]09月20日16:00闪断更新公告
计划将于 2026年09月20日16:00 ~ 16:10 期间进行服务器闪断更新
10月09日10:00-16:00停机维护
```

## 触发

满足任一条件即记为更新事件：

1. 公告解析出维护时间窗。
2. 官方版本接口的 `clientVersion` 或 `resVersion` 发生变化。

## 位置

更新是独立的运行，不属于前置操作：

- 有自己的触发：公告解析出的维护时间，或版本接口发现变化。
- 有自己的步骤：启动游戏、进入更新、等待下载与安装、判定完成。
- 有自己的判定与通知：更新失败单独通知。
- 与日常的关系由编排层处理：开跑前检查是否还有未完成的更新，有则先更新再跑日常。

前置操作只做「让环境就绪」，不承担更新。

## 更新日流程

```text
1. 解析公告 → 排出更新任务（时间 = 维护结束 + 5 分钟缓冲）
2. 若当天日常触发点距更新在 3 小时内 → 该轮日常让路
3. 到点 → 启动模拟器与游戏
4. 等待更新界面 → 等待下载与安装
5. 判定完成：版本号变化，或出现登录界面 / 主界面可点击
6. 补跑当天日常
7. 记录版本号与总耗时
```

更新运行同样适用判定等级：脚本口径看更新任务的退出状态，画面口径看更新完成后的登录界面或主界面，双证据两者都看；画面证据缺失记判不出。

## 期间约束

- 只在白天执行，默认 06:00–22:00，可配置。
- 维护未结束时，等到结束时间加缓冲再试。
- 单次更新最长 45 分钟，可配置；超时收手。
- 同一天只成功更新一次；失败可在窗口内重试一次。

## 失败处置

| 情形 | 处置 |
|---|---|
| 公告抓不到 | 用版本接口兜底；仍失败则按平时计划跑 |
| 维护未结束 | 等到结束加缓冲 |
| 更新下载卡住 | 超时重试一次；仍失败停手通知 |
| 更新后游戏异常 | 重启游戏一次；仍异常停手 |
| 更新后日常失败 | 按日常兜底处理，结论照常出 |

## 与日常的关系

- 更新日：先更新，后日常；临近更新的那一轮日常让路，由更新任务收尾时补跑。
- 非更新日：按计划执行。

## 与脚本配置的关系

游戏或脚本升级后，脚本自身的配置会出现新选项（例如新活动关卡）。开跑前的对账会发现这些差异；默认策略「以脚本为主」会把它们吸收进程序侧，并在冲突页留下记录。

## 安全

- 更新由游戏客户端完成，程序只负责启动、等待与判定，不替换任何文件。
- 更新期间不点击游戏内危险区域。
- 公告解析结果保留原文与抓取时间，可追溯。
