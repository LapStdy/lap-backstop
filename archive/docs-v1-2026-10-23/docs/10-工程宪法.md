# 10 · 工程宪法

[返回总览](00-总览与索引.md)

## 这份文件为什么存在

项目越做越难改，通常不是技术难题，而是规矩慢慢失守：为了赶进度绕一下、为了省事复制一段、为了不改旧代码多写一个分支。每一次都合理，合起来就把项目压垮。

这份文件把「什么不能做」和「怎么证明做对了」固定下来。规矩分两类：能用机器检查的，交给门禁（[12](12-测试与质量门禁.md)）；不能机器检查的，交给评审清单（[13](13-变更与演进.md)）。

## 十条不可妥协

1. **边界先于功能。** 模块只能按依赖方向调用；`web` 不碰数据库与模拟器，`adapters` 不碰界面与 AI。违反由依赖检查拦下。
2. **流程是数据。** 任务、步骤、计划、选项写在配置里；代码里不出现「方舟日常的第三步是什么」这类业务流程分支。
3. **单一编辑入口。** 程序侧是配置与状态唯一的编辑入口；脚本侧配置是对账副本，出现差异必须能被发现、由人或默认策略决定、并留痕。任何配置都不在两个文件里各写一份默认值。
4. **判定有证据，动作有记录。** 每条结论附可复核的证据（截图、日志片段或退出状态），证据类型由判定等级决定；没有事件的动作查不到。
5. **修 bug 先写失败用例。** 先让它红，再让它绿；没有用例的修复，下次还会坏。
6. **门禁不过不算完成。** 完成由工具判定，不由感觉判定。
7. **小步前进。** 一次改动只做一件事；结构性改动先写 ADR，再动手。
8. **绕行有到期日。** 任何临时绕行都要进 `DEBT.md`，写清原因、影响与归还期限。
9. **文档同改。** 改接口、改结构、改流程，同一次改动里把对应文档改掉；文档与代码不一致时，文档算错。
10. **不确定就问。** 需求不清、影响面不清、代价不清时停下来问，不猜着写。

## 腐化模式对照表

| 症状 | 根因 | 对应规矩 |
|---|---|---|
| 改一处，崩好几处 | 模块耦合、边界模糊 | 1、[11 依赖方向](11-代码规约.md) |
| 加功能必须改旧代码 | 流程写死在代码里 | 2 |
| 不敢重构 | 没有测试兜底 | 5、[12 门禁](12-测试与质量门禁.md) |
| 配置互相打架 | 多个编辑入口、没有对账 | 3 |
| 线上问题查不到原因 | 没有证据与记录 | 4 |
| 补丁越积越多 | 绕行没有期限 | 8 |
| 文档没人信 | 文档与代码脱节 | 9 |
| 每次都由不同风格写成 | 没有统一规约 | [11](11-代码规约.md) |
| 半成品功能混进主线 | 完成定义缺失 | [13 DoD](13-变更与演进.md) |

## 违反时怎么办

| 情形 | 做法 |
|---|---|
| 需求或影响面不清 | 停下来说明缺什么，等人回答；不猜 |
| 必须破例 | 记进 `DEBT.md`：为什么破、影响是什么、何时归还 |
| 觉得规矩本身不对 | 提 ADR 说明冲突与替代方案，人确认后修改本文 |
| 发现别人或 AI 违反 | 先把这一处修正，再继续；不"下不为例" |

## 谁受约束

人、AI、脚本一视同仁。AI 产出的代码同样过全部门禁与评审清单，不因为「看起来对」而豁免。

## 修改本文

- 增加一条：说明它挡住哪个已发生的具体问题。
- 删除一条：说明为什么不再需要，并确认不会让老问题回来。
- 修改走 ADR，人确认后生效。
