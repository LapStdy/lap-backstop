# 01 · 需求与边界

[返回总览](00-总览与索引.md)

本文件回答：平台要满足哪些可验收的需求、首批插件各自承担什么、边界在哪里。需求编号同时是测试用例名、验收清单条目与插件契约测试的锚点。

## 1. 定位、分工与编号

- 产品：通用调度与监督平台，托管 Windows 电脑上的外部自动化脚本。
- 使用者：机主本人，单人；一台常开 Windows 电脑，一个内核，一份数据库。
- 首批插件：MAA 与 MAAEnd（MaaFramework 系）；方舟环境、终末地环境是两个 EnvironmentProvider 的能力位。

| 层 | 负责 | 不负责 |
|---|---|---|
| 内核 | 调度、作业生命周期、环境状态、租约、事件、恢复策略、插件宿主、API | 具体脚本怎么启动、日志怎么写、画面怎么认、配置怎么投影 |
| 插件 | 环境探测与准备、脚本启停与观测、结论与证据、配置投影、通知、建议 | 调度语义、幂等、租约、事件存储 |
| 客户端 | 展示与操作，全部经 HTTP API 与 SSE | 业务判断、状态真相、本地排程 |

编号分段：P-1xx 调度、P-2xx 资源与环境、P-3xx 作业、P-4xx 插件、P-5xx 验证与证据、P-6xx 恢复、P-7xx 通知与远程、P-8xx 观测、P-9xx 多机、P-10xx AI；M-1xx 与 M-2xx 是 MAA 与 MAAEnd 插件，A-1xx 与 E-1xx 是方舟与终末地环境，N-1xx 是非功能指标，S-1xx 是安全边界，AC-x 是整体验收。调度与作业语义见 [09](09-调度与作业语义.md)，插件契约见 [05](05-插件与适配器.md)，接口见 [03](03-数据模型与接口.md)。

## 2. 平台需求

### P-100 调度

| 编号 | 需求 | 判据 |
|---|---|---|
| P-101 | 支持 cron、at、interval 三类 Schedule；时区以 IANA 名称存储 | 创建后 API 返回 next_run_at（UTC）与本地时区展示；跨夏令时的发生点与按 zoneinfo 手算一致 |
| P-102 | 幂等键为 `<schedule_id>:<scheduled_at>`（UTC，截断到整秒） | 同一发生点重复触发、双击、补跑、崩溃恢复四种情形各跑一次，job_runs 中该发生点只有 1 行 |
| P-103 | 错过策略 catch_up 取 run_once / skip / window | 机器离线 6 小时后启动：run_once 补 1 次，skip 补 0 次，window 在 window_minutes 内补 1 次、超出补 0 次 |
| P-104 | coalesce 打开时，同一 Schedule 连续发生点合并为一次运行 | 合并后只有 1 个 JobRun；`run.created` 的 `merged_scheduled_ats` 列出被合并的其它发生点（UTC ISO8601，升序） |
| P-105 | 队列按 priority 降序、scheduled_at 升序、created_at 升序 | 三个不同优先级的运行同时到期，执行顺序与 priority 一致；同优先级按计划时间而非入队时间 |
| P-106 | deadline_minutes 到点仍未进入 executing 的运行不启动 | 该 JobRun 记 failed（错误码 E_DEADLINE）并发通知，不产生脚本进程 |
| P-107 | preheat_minutes 前进入 prepare，到 scheduled_at 才进入 executing | 环境冷启动耗时 55 秒的场景下，executing 起点等待环境就绪的耗时为 0 |
| P-108 | keep_warm_minutes 内环境保持 ready | 两次触发间隔小于窗口时不重复冷启动；超出后按 cleanup 关闭并记事件 |

### P-200 资源与环境

| 编号 | 需求 | 判据 |
|---|---|---|
| P-201 | 环境状态机 unknown / off / booting / ready / busy / degraded / failed 由内核维护 | 每次迁移写 `env.state.changed`，含 from_state、to_state 与 probe 结果；插件不能直接改状态 |
| P-202 | ready 由插件的 probe 判定，内核只采信结论 | probe 超时或异常记 degraded，不推断 ready；failed 后不再自动 prepare，直到策略允许或人工 reset |
| P-203 | prepare 幂等：已 ready 直接返回成功 | 连续调用 3 次 prepare，环境只启动一次 |
| P-204 | reset 可从任意状态回到 booting | reset 后 60 秒内重新 probe；连调 2 次不产生第二个引导进程 |
| P-205 | 资源租约 free → leased → expiring → released，带 TTL 与续租 | 同一资源并发申请 2 个租约，第二个排队；TTL 到期未续租自动回收并记事件，运行按 09 的租约过期规则处置 |
| P-206 | 租不到资源的运行停在 queued，不丢失 | 队列按 priority、scheduled_at、created_at 排序；资源释放后 5 秒内被唤醒 |
| P-207 | cleanup 释放租约并按保温策略处置环境 | 运行结束后该资源的 leased 数为 0；保温窗口内环境保持 ready |

### P-300 作业生命周期

| 编号 | 需求 | 判据 |
|---|---|---|
| P-301 | JobRun 状态机 scheduled → queued → preparing → waiting → executing → verifying → cleaning → succeeded \| failed \| unknown；另有 cancelled 与 recovering | 非法迁移被拒绝并记事件；cleanup 完成并释放租约后才进入终态 |
| P-302 | 四个 Phase（prepare / execute / verify / cleanup）各记 pending / running / ok / failed / skipped / timed_out | 每次运行 run_phases 至少 4 行，含开始、结束、耗时 |
| P-303 | 每次重试 attempt 递增，失败原因归到对应 attempt | 运行详情列出每个 attempt 的起止、错误码、证据 |
| P-304 | 取消：POST /api/v1/runs/{id}/stop，在阶段边界生效 | 状态记 cancelled，不计 failed；超时未退由内核强杀；停止后无遗留租约与插件进程 |
| P-305 | 手动立即跑：POST /api/v1/schedules/{id}/run 必须带 Idempotency-Key | 同一 key 重复提交只建 1 个 JobRun，第二次返回同一运行；缺失 key 返回 E_BAD_REQUEST |
| P-306 | JobTemplate 与 Schedule 分离，一个模板可被多个计划引用 | 修改模板不影响进行中的运行；运行开始时冻结参数快照 |
| P-307 | 进程崩溃重启后恢复未完成运行，不重复执行 | 在 executing 阶段终止内核再启动，该发生点仍只有 1 个 JobRun，状态收敛到 queued、recovering、unknown 或 failed |

### P-400 插件与契约

| 编号 | 需求 | 判据 |
|---|---|---|
| P-401 | manifest 必填 id、name、version、api_version、capabilities、config_schema、requires；description 与 error_map 可选 | 缺必填字段插件不被加载，报 E_PLUGIN_MANIFEST |
| P-402 | api_version 为整数，插件声明兼容范围，内核拒绝不兼容 | 装一个版本超范围的 fake 插件，内核记拒绝原因且不影响其他插件 |
| P-403 | 能力按需声明；缺能力时内核降级而非报错 | 无 Verifier 的插件跑完后 verdict 记 unknown；无 Notifier 时只写事件不发通知 |
| P-404 | 配置以 JSON Schema 声明；内核做校验、表单生成、迁移，payload 不透明存储 | 非法值被拒（400 带字段路径）；合法值落库并在插件重启后原样回读 |
| P-405 | 插件在 worker 进程运行，超时与取消由内核控制，插件不得直连内核数据库 | 插件内直接打开内核 SQLite 被拒；phase 超时后内核终止该 worker 并记事件 |
| P-406 | 每个插件跑同一套 capability 契约测试，fake 覆盖瞬时/慢/永不就绪、成功/失败/挂起/部分完成 | MAA 与 MAAEnd 过同一套用例；终止一个插件 worker 后内核仍服务 /health 与 status |

### P-500 验证与证据

| 编号 | 需求 | 判据 |
|---|---|---|
| P-501 | Verifier.verify 返回 Verdict（completed / failed / unknown）与 reason、evidence 引用 | 三种取值各有用例；无 evidence 的 completed 被内核拒绝 |
| P-502 | 每条结论至少 1 条证据；缺证据记 unknown | 人为删掉证据后重跑判定，verdict 为 unknown 且原因写明缺证据 |
| P-503 | VerificationPolicy 归插件与配置层，内核只存 verdict | 内核表结构中没有判定等级字段；切换策略不改内核代码 |
| P-504 | 证据矛盾记 unknown | 脚本报完成、结束画面非主界面时结论为 unknown，不降级为 completed |
| P-505 | 证据默认保留 30 天，只读、按运行归档；过期后 verdict 保留并标注证据已过期 | 过期扫描后 verdict 仍可查，证据下载返回 410 与过期说明；任何 API 都不能改写证据文件 |
| P-506 | 判定不依赖第三方数据接口 | 断网且未登录账号时，verdict 仍可由日志与画面得出 |

### P-600 恢复

| 编号 | 需求 | 判据 |
|---|---|---|
| P-601 | 恢复由 policy 驱动：max_attempts、backoff、reset 环境、重启脚本、停手 | 每个动作在事件流中可见，顺序符合 policy |
| P-602 | 恢复动作路由到插件能力，内核只做调度 | 替换插件后恢复动作不变；内核不出现 MAA 专有恢复分支 |
| P-603 | 升级顺序：重试 → 复位环境 → 重启脚本 → 停手 | 连续失败用例按此顺序推进，不跳级；换参数由 policy 配置，不单列为动作 |
| P-604 | 停手必须通知，附证据与原因 | 停手后 60 秒内收到通知；内容含运行 id、错误码、证据入口 |
| P-605 | 恢复有预算：单次运行总时长与 attempt 数上限 | 超限直接停手，不再退避重试；事件写明预算耗尽 |
| P-606 | 同一错误码连续 N 次后不再重试 | N 由 policy 配置；达到后转停手并标记重复失败 |

### P-700 通知与远程

| 编号 | 需求 | 判据 |
|---|---|---|
| P-701 | 通知经 Notifier 插件发送，发送失败不影响运行结论 | 断开通知通道后跑一轮，JobRun 仍 succeeded，事件记 notify.failed |
| P-702 | 每次运行结束都发通知，不设静音时段 | succeeded / failed / unknown / cancelled 四类各发一条 |
| P-703 | 停手与环境 failed 单独发一条高优先级通知 | 与普通运行结论可区分（标题前缀或优先级字段） |
| P-704 | /api/v1 除 /health 外都要 Bearer token | 无 token 或错 token 返回 401 与 E_AUTH，不返回数据 |
| P-705 | 远程与本地共享同一 API，无隐藏本地通道 | 手机 APK 与桌面窗口都能看状态、叫停、启停计划；完整编辑器在桌面窗口 |
| P-706 | 远程只经局域网或 Tailscale，不暴露公网 | 默认只监听回环；开启远程后监听 Tailscale 地址，端口不对公网开放 |
| P-707 | 界面离线时只读 | 断网后写操作按钮禁用并说明原因，不排队重放 |
| P-708 | 写接口幂等：POST 接受 Idempotency-Key，PUT 接受 If-Match | 重复 POST 返回同一资源；过期 If-Match 返回 409 |

### P-800 观测与事件

| 编号 | 需求 | 判据 |
|---|---|---|
| P-801 | 事件 append-only，运行内 seq 单调递增，SSE 可 Last-Event-ID 续传 | 重启后 seq 不回退、不重复；SSE 带 Last-Event-ID 只补缺失段 |
| P-802 | 事件表覆盖状态迁移、阶段、证据、结论、通知、恢复、配置变更、插件加载，每类有 type 与 payload；SSE 对外子集见 [03](03-数据模型与接口.md) | 契约测试逐类校验；关键动作（配置写入、插件加载、停止、恢复）的事件与日志成对存在 |
| P-803 | /api/v1/status 返回首屏全量快照 | 一次请求含当前运行、队列、环境状态、最近结论与下次触发 |
| P-804 | 任一次运行可按事件流回放 | 回放顺序与 seq 一致，证据按事件引用可打开 |
| P-805 | SSE 慢客户端不阻塞内核，丢弃时明确要求重新同步 | 模拟慢读客户端，内核写入延迟不升高；客户端收到 reset 提示后重取快照 |

### P-900 多机

| 编号 | 需求 | 判据 |
|---|---|---|
| P-901 | 一台机器一个内核、一份数据库、一个 token 域 | server_id 在 /health 与 /status 中返回，两台机器不同 |
| P-902 | 多机不共享调度：每台独立排程，不设中心调度器，不做跨机租约 | 两台机器各自运行；客户端一期只连一台主机，切换主机不在本期 |
| P-903 | 数据可整体备份迁移（数据库 + 证据目录） | 迁移到另一台机器后恢复，幂等键不导致重复执行 |

### P-1000 AI

| 编号 | 需求 | 判据 |
|---|---|---|
| P-1001 | Advisor 是可选插件，不装也能跑全部功能 | 卸载 Advisor 后调度、运行、判定、通知均正常 |
| P-1002 | 输入只给证据摘要与结构化上下文，不上传凭据与完整配置 | 抓取一次调用载荷，不含 token、密码、绝对用户目录 |
| P-1003 | 输出是建议草稿，落地前经规则校验 | 越权建议（改路径、跳判定、动黑名单区域）被拒绝并记事件 |
| P-1004 | 预算：单次运行调用次数与金额上限 | 达到上限后转规则路径，事件记 budget_exhausted |
| P-1005 | 每次调用留审计（输入摘要、输出、耗时、花费、模型名） | advisor_calls 可查，可按运行过滤；AI 不可用时界面标注原因与配置位置 |

## 3. 首批插件需求

### M-100 MAA 插件

| 编号 | 需求 | 判据 |
|---|---|---|
| M-101 | manifest id=maa，声明 EnvironmentProvider、ScriptAdapter、Verifier、ConfigProjection 四项能力 | 契约测试四项全过；缺一项则加载被拒 |
| M-102 | 环境：MuMu 12（H:/MuMuPlayer）VM0 明日方舟，Android 15，adb 127.0.0.1:16384，分辨率 1280×720 | probe 在 adb 可连且可截图时返回 ready；断开时 degraded |
| M-103 | 启动：MAA 位于 H:/MAA，冷启动约 55 秒，启动到资源加载完成约 72 秒 | prepare 在超时前完成；超过 launch_timeout_s 未加载完成记 failed（E_SCRIPT_RESOURCE_TIMEOUT） |
| M-104 | 观测信号取 gui.log 与 asst.log | gui.log 至少解析「正在连接模拟器」「完成任务: X」「任务出错: X」「任务已全部完成！」「游戏掉线，停止任务」「Post actions」；asst.log 至少解析 AllTasksCompleted、TaskChainStart/Completed/Error、SubTaskExtraInfo(SanityBeforeStage) |
| M-105 | 开始唤醒 66 秒超时是明确失败信号 | 出现该超时后不再等待，转恢复：复位游戏或重启模拟器 |
| M-106 | stop 先调 MAA 停止接口，再确认进程退出 | 10 秒内 MAA 进程消失；未消失由内核升级为终止进程并记事件 |
| M-107 | 配置投影：写 gui.new.json 前检测 MAA 是否运行并备份，写后回读校验 | MAA 运行时拒绝写入（E_CONFIG_LOCKED）；写入失败可从备份回滚 |
| M-108 | 程序接管完成后动作：游戏与模拟器由环境 cleanup 关闭 | 插件把 MAA 的退出游戏、退出模拟器 PostActions 置为不动作；运行结束后环境仍可保温 |
| M-109 | 判定按 MAA policy 三档（script 脚本口径 / screen 画面口径 / dual 双证据）给结论 | 三种档位各有用例；缺画面证据时 dual 记 unknown |
| M-110 | 错误映射按领域前缀声明（E_ENV_、E_SCRIPT_、E_CONFIG_、E_VERIFY_），至少覆盖掉线、任务出错、唤醒超时、资源加载超时 | 错误码到恢复动作一一对应；未知错误落默认策略并附原始日志片段 |

### M-200 MAAEnd 插件

| 编号 | 需求 | 判据 |
|---|---|---|
| M-201 | manifest id=maaend，声明 EnvironmentProvider、ScriptAdapter、Verifier 三项能力；与 MAA 可同时安装，由 JobTemplate 的 plugin_id 路由 | 契约测试三项全过；两个插件并存时各走各的，互不读取配置 |
| M-202 | 走 MaaFramework 接入，不依赖 MAA GUI 配置文件 | 插件配置全部来自 manifest schema；运行不读取 gui.new.json |
| M-203 | 结论取 MaaFramework 的任务结果与识别回调，不以日志文本为唯一依据 | 结论附带结构化结果与截图；无结果时记 unknown |
| M-204 | 未实测能力在 TASKS「技术验证」列出，插件文档只写契约要求与已确认事实 | 插件文档不含未验证的端口、路径、回调名 |
| M-205 | 先用 fake 通过契约测试，再接真机 | fake 通过后真机失败只允许出在适配层，不允许改内核 |

### A-100 方舟环境

| 编号 | 需求 | 判据 |
|---|---|---|
| A-101 | 环境固定为 MuMu 12 的 VM0 实例，adb 端口 127.0.0.1:16384，分辨率 1280×720 | probe 读到包名与分辨率，不符时 failed |
| A-102 | 就绪判据是主界面可识别且可截图，不是进程存在 | 进程在但停在启动动画时 probe 返回 booting |
| A-103 | MuMu 是桌面 GUI 程序，必须在交互式会话内运行，不能作为 Windows 服务启动 | 在 Session 0 启动的尝试失败并记为环境错误 |
| A-104 | warm：keep_warm_minutes 内不关闭模拟器，空闲超时后关闭 | 两次运行间隔 10 分钟、保温 30 分钟时，第二次无冷启动 |
| A-105 | 截图双通道：MuMu 原生 10–150 毫秒，adb exec-out 约 600 毫秒 | probe 与实时观测走原生通道；证据可用任一通道，事件记录通道与耗时 |
| A-106 | 一台机器同一时刻只允许一个方舟作业占用环境 | 并发第二个作业排队，不启动第二个模拟器实例 |
| A-107 | 断线/掉线是高频故障：恢复含重连 adb、重启游戏、重启模拟器 | 三类故障各有用例，恢复到 ready 后继续本次运行 |
| A-108 | 更新与维护让路是独立作业类型，不作为前置步骤 | 维护窗口内的日常作业按策略跳过或延后，事件写明原因 |

### E-100 终末地环境

| 编号 | 需求 | 判据 |
|---|---|---|
| E-101 | 只保留 EnvironmentProvider 契约位，接入排在 MAA 之后；内核不得出现终末地专有字段 | 契约测试由 fake 环境覆盖；代码评审检查 core 无 endfield 相关标识 |
| E-102 | 接入时需提供 probe、prepare、reset、cleanup、warm 五个动作 | 缺任一动作不满足环境契约 |
| E-103 | 接入排在 P2（MAAEnd 插件），先过 capability 契约测试再排期 | TASKS 的 P2 有 MAAEnd 实现项；接入前有独立验收清单 |
| E-104 | 接入时另立环境文档与参数，不复用方舟参数 | 两套环境配置互不影响，可同时安装 |

## 5. 安全边界

| 编号 | 约束 | 判据 |
|---|---|---|
| S-101 | 不修改游戏客户端文件，不注入、不破解、不绕过检测 | 仓库与运行目录无客户端改动；动作只经截图与点击 |
| S-102 | 不修改 MAA 程序文件，只读写配置与日志 | 写入前备份、可回滚；程序目录哈希保持不变 |
| S-103 | 点击使用固定安全坐标并设危险区域黑名单 | 黑名单区域（如清除缓存）点击被插件拒绝并记事件 |
| S-104 | 控制面只在局域网或 Tailscale 可达 | 端口扫描公网地址不可达；默认监听回环 |
| S-105 | token 只存本地配置，不写日志、不进证据、不进备份导出 | 全量日志与证据检索不到 token 明文 |
| S-106 | AI 给出的坐标与动作必须经白名单与黑名单校验后执行 | 越界坐标被拒绝；执行前有校验事件 |
| S-107 | 插件不得直接写内核数据库，不得读其他插件配置；路径参数限制在配置声明的根目录内 | 插件进程内的写入与跨插件读取被拒绝；含 .. 的路径被拒（E_CONFIG） |
| S-108 | 截图与日志只对授权客户端可见 | 无 token 的请求拿不到证据内容 |

## 7. 不在范围

- 游戏内作弊、修改客户端、绕过检测。

## 8. 需求与测试对应

- 测试用例名以需求编号开头，例如「[P-101] cron 下次触发计算」；一条需求至少一条自动化用例。
- 契约测试按 capability 组织，每个插件跑同一套用例，见 [05](05-插件与适配器.md)。
- 无法自动化的条目（7 天无人值守、真机 App 交互）进验收清单，由 AC 编号引用。
- 需求变更先改本文件，再改测试；不得只改测试绕过需求。

| 测试层 | 主要覆盖 | 对应需求 |
|---|---|---|
| 单元 | 调度计算、状态机迁移、幂等键、租约 TTL | P-1xx、P-2xx、P-3xx |
| 契约 | 每个插件的每项 capability | P-4xx、M-1xx、M-2xx |
| 集成 | API + SQLite + SSE + worker | P-3xx、P-7xx、P-8xx |
| 场景 | 方舟日常、断线、唤醒超时、错过补跑、保温 | M-1xx、A-1xx、AC-1–AC-6 |
| 端到端 | 桌面 GUI 与 APK 操作全链路 | P-705、AC-7 |
| 故障注入与 soak | 插件崩溃、数据库锁、慢客户端、磁盘写满、7 天连续运行 | P-405、P-805、N-101、N-109 |
