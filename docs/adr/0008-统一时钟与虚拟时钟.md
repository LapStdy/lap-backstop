# ADR 0008 · 统一时钟与虚拟时钟

- 状态：accepted
- 日期：2026-10-24

## 背景

调度、超时、退避、租约 TTL、看门狗都依赖时间。直接读系统时间会让测试不可控：等待真实秒数、时序不稳定、无法覆盖休眠与校时。墙钟还会被用户调整或 NTP 校正，单调量才是超时的可靠依据。

## 决策

1. 内核只通过 `contracts.Clock` 取时间：`monotonic()` 用于超时、退避、租约与看门狗，`utc_now()` 用于调度、记账与展示。
2. 生产实现是 `core.clock.SystemClock`：单调读走 `time.monotonic`，UTC 读带时区。
3. 测试实现是 `core.clock.VirtualClock`：由调用方推进，墙钟可单独跳变以覆盖休眠恢复与校时，单调值只按差值前进、不倒退。
4. 内核组件与插件都只接受注入的 Clock；业务代码不调用 `time.time`、`datetime.now`。
5. 数据库存 UTC 时间，展示按用户时区换算；重启后单调时钟不跨进程，按持久化的 UTC 截止时间重建剩余量。
6. 日志的 `at` 也走可注入的 Clock，便于在虚拟时钟下断言日志时间。

## 后果

- 调度与超时测试用虚拟时钟按秒推进，不 sleep、不等待真实时间。
- 休眠、校时、跨进程重启的时序差异有统一的解释口径。
- 测试必须显式推进时钟；忘记推进时超时不会自然发生，属于测试写法问题而非实现缺陷。

## 替代方案

| 方案 | 不采纳的原因 |
|---|---|
| 业务代码直接读系统时间 | 测试不可控，休眠与校时导致的漂移无法覆盖。 |
| 引入 freezegun 之类的全局时间冻结 | 依赖第三方改写全局状态，与「注入 Clock」的分层约束冲突。 |
| 只用墙钟算超时 | 墙钟跳变会让超时提前或延后，租约与看门狗失去意义。 |
