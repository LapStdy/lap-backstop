# ADR 0003 · 验证策略插件化

- 状态：accepted
- 日期：2026-10-23

## 背景

平台托管多种脚本，每种脚本的「完成」证据不同。MAA 的完成来自 `gui.log` 的队列完成行、任务链信号与结束画面；终末地的完成来自 MaaFramework 的任务信号与它自己的画面。内核若内置「主界面模板命中」「理智下降」这类判据，就把方舟的领域知识写进了平台，接入第二个脚本时还要改内核。

内核又必须统一存证、回放、通知与恢复，所以结论与证据的形状必须稳定。需要划分：哪些是平台不变量，哪些是某个脚本的验证口径。

## 决策

1. **内核定义三个类型。** `Verdict`（`status` 取 `completed`、`failed`、`unknown`，附 `policy_id`、`confidence`、`reason`、`checks`（`list[CheckResult]`，每项含 `name`、`status`、`detail`、`evidence_ids`、`at`）、`evidence_ids`、`created_at`）、`Evidence`（`id`、`kind`、`source`、`path`、`sha256`、`summary`、`created_at`）、`VerificationPolicy`（`id`、`verifier_plugin_id`、`required_evidence`、`params`）。字段与 [05](../05-插件与适配器.md) 一致。
2. **内核不定义证据语义。** `kind` 只用于存储与展示分类；一条日志行说明什么、一张截图算不算完成，由插件的验证策略解释。
3. **验证策略由 JobTemplate 存完整结构，由插件实现。** 模板保存完整的 `VerificationPolicy`（含 `id`，模板创建时生成 UUID）；内核不设策略注册表。MAA 的脚本口径、画面口径、双证据是 `params.mode` 的三个取值，属于 MAA 插件；终末地的策略属于 MAAEnd 插件。策略在作业开始时冻结，运行中不改。
4. **内核只做机械动作。** 调用 `Verifier.verify`，校验 `status` 合法、`evidence_ids` 都存在、`policy_id` 等于模板保存的策略 `id`，然后存证、发事件、按策略展示。内核不解析日志、不读模板、不计算理智。
5. **证据可信度排序不进内核。** 「画面高于进程与日志」是某个脚本的经验，不是平台不变量；排序写在插件策略里，由插件决定哪些证据参与结论。
6. **策略自带声明。** 每个策略在模板里声明 id、验证器插件、所需证据类型与 params；内核按模板里的策略 id 路由，不按脚本名分支。
7. **只有 `Verifier` 产生结论。** Advisor 的归因、通知插件的投递结果都不能写 `Verdict`；结论与作业状态分离，`completed` 映射为 `JobRun.succeeded`，`failed` 与 `unknown` 同名直传。

## 后果

- 新增脚本只需实现 `Verifier`，内核判定代码不变；验证口径变更只升插件版本，不触发契约升级。
- 证据按统一结构存证、回放与展示；界面显示 `policy_id`，用户能看出结论依据的是哪套口径。
- 契约测试要求每个 `Verifier` 覆盖三态、证据引用完整、同一证据同一策略结果稳定；不满足的插件不注册。
- 不同插件的严格程度可能不同，这是允许的：严格程度属于策略，平台只保证结论有证据、可复核。
- 验证策略必须通过契约测试的 `Verifier` 用例；判据变更写进插件版本与证据。
- 回放使用当时冻结的策略参数，不用当前参数重算历史结论。
- MAA 的三种口径见 [plugins/maa](../plugins/maa.md)，终末地的策略见 [plugins/maaend](../plugins/maaend.md)。

## 替代方案

| 方案 | 不采纳的原因 |
|---|---|
| 内核内置三种口径 | 口径来自 MAA 日志与方舟画面，接入第二个脚本就要改内核 |
| 内核内置证据可信度排序 | 排序是游戏经验，换脚本即失效，且会掩盖插件差异 |
| 插件只返回布尔完成 | 丢失 `unknown` 与证据，无法回放、无法解释、无法追责 |
| 由 Advisor 参与判定 | AI 输出是建议，不可复核，不能作为结论依据 |
