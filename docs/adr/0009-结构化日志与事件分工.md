# ADR 0009 · 结构化日志与事件分工

- 状态：accepted
- 日期：2026-10-24

## 背景

排障需要现场细节，判定与回放需要可靠事实。两者混在一起会带来两个问题：自由文本日志无法按字段检索与聚合；日志作为判定依据时，缺少顺序、幂等与持久化保证。密钥与截图字节又必须留在日志之外。

## 决策

1. 日志与事件分工：事件写 `run_events` / `events_global` 两张表，append-only、有单调序号、可回放、可作证据；日志只供排障，不作判定依据。
2. `contracts.Logger` 只接受字段映射：`debug` / `info` / `warn` / `error`，调用方给 `event` 与上下文键，不拼自由文本。
3. `core.logging.JsonLineLogger` 每行写一条 JSON，固定含 `at`（UTC）与 `level`，并保留调用方字段；事件名缺失时记 `unspecified`，保证每行都能按 `event` 检索。
4. `core.logging.NullLogger` 用于测试与不关心输出的路径；生产日志路径由启动参数决定，日志级别与保留在宿主层配置。
5. 不打印 token、口令、Cookie、截图字节与完整个人路径；插件上下文里的密钥只经 `ctx.secrets` 按名读取。
6. 捕获异常后要么处置、要么带上下文重抛；自愈类异常记 WARNING 并继续，需要人看的记 ERROR。

## 后果

- 运行过程可回放：状态迁移、阶段、信号、证据、结论都有事件，日志丢失不影响判定。
- 日志可按 `event`、`run_id`、`plugin`、`level` 聚合；同一类日志的字段名固定。
- 日志写入不参与事务，日志失败不影响业务；事件写入与业务状态在同一事务里，失败会回滚。
- 日志量随排障级别变化，不需要与事件保留期一致。

## 替代方案

| 方案 | 不采纳的原因 |
|---|---|
| 用日志作为判定与证据来源 | 无序号、无事务、可被清理，不能作为可复核事实。 |
| 只写自由文本日志 | 无法按字段检索与统计，排障成本高。 |
| 把日志也写进数据库 | 放大量与事务开销，且与「事件才是事实」的职责重复。 |
