# 08 · 宿主与运维

[返回总览](00-总览与索引.md)

本文回答：平台跑在什么 Windows 宿主上，机器重启、断电、断网、核心崩溃、版本升级时靠什么把服务拉回来。进程与模块见 [02](02-架构.md)，表与接口见 [03](03-数据模型与接口.md)，改动流程见 [13](13-变更与演进.md)。

## 宿主基线

| 项 | 要求 |
|---|---|
| 操作系统 | Windows 10/11 x64，开启硬件虚拟化 |
| 账号 | 专用本地账号 `backstop`，属 Administrators 组，只允许本机登录 |
| 会话 | 交互式登录会话；核心不由 Windows 服务托管 |
| Python | 3.12 及以上（宿主实测 3.14.3） |
| 模拟器 | MuMu 12 装在 `H:\MuMuPlayer`，实例 VM0 跑明日方舟（Android 15），adb `127.0.0.1:16384` |
| 外部脚本 | MAA 6.20.x 装在 `H:\MAA` |
| 显示 | 1280×720，缩放 100%；显示器可关，会话不得锁屏 |
| 电源 | 交流常供；电池只作短时兜底 |
| 网络 | 有线优先；Tailscale 提供外出访问地址 |

核心必须跑在交互式会话内。MuMu 是桌面 GUI 程序，服务所在的 Session 0 没有桌面合成与 GPU 上下文，窗口截图、点击、画面识别都不可用；核心、模拟器、游戏因此处于同一登录会话。

## 自动登录

无人值守的起点是「重启后不需要有人按键」。自动登录没配好，整条恢复链路在第一步就断。

| 项 | 做法 |
|---|---|
| 注册表 | `HKLM\SOFTWARE\Microsoft\Windows NT\CurrentVersion\Winlogon`：`AutoAdminLogon=1`、`DefaultUserName=backstop`、`DefaultDomainName=<机器名>` |
| 口令 | 用 Sysinternals Autologon 写入 LSA secret；`DefaultPassword` 留空，不存明文 |
| 锁屏 | 关闭 Ctrl+Alt+Del 强制、屏保与动态锁；锁屏会让模拟器窗口不可交互 |
| 更新重启 | 关闭「更新后自动重启」的立即重启行为，更新安装时间避开调度窗口 |
| 自检 | 核心启动时读上述注册表值，写入事件 `host.autologon_checked`；值不为 1 或用户名为空时发一条 warn 通知 |
| 失败兜底 | 自动登录失败时机器停在登录界面：核心不会启动，平台自身也不会发出任何报警 |

宿主当前 `AutoAdminLogon=0`、`DefaultUserName` 为空，上述自检会持续报警，直到注册表配置到位。

## 计划任务

核心每次启动按 settings 注册或修复四个计划任务（`register_tasks` 关闭时不注册，进程内测试用这个开关）；同一份注册逻辑也挂在 `lap-backstop tasks register` 与 `POST /api/v1/host/tasks/register` 上。

| 任务名 | 触发器 | 动作 | 设置 |
|---|---|---|---|
| `lap-backstop-core` | 登录时，延迟 30 s | `app\current\lap-backstop.exe serve` | 失败后每 1 分钟重试，最多 3 次；不因运行超时停止 |
| `lap-backstop-watchdog` | 登录时，之后每 5 分钟 | `app\current\lap-backstop.exe watchdog check` | 单实例；不因运行超时停止 |
| `lap-backstop-backup` | 每日 04:00 | `app\current\lap-backstop.exe backup` | 允许唤醒计算机；失败不阻塞调度 |
| `lap-backstop-evidence-mirror` | 每周日 04:30 | `app\current\lap-backstop.exe evidence-mirror` | 允许唤醒计算机；失败不阻塞调度 |

- 「Stop the task if it runs longer than」一律不勾；核心是长驻进程。
- 「Start the task only if the computer is on AC power」关闭，否则电池时任务根本不启动。
- 实例策略用「Do not start a new instance」，与新实例排队冲突时以互斥量为准。
- 任务以 XML 导入，定义文件写在 `data\host\tasks\<任务名>.xml`，注册时按定义覆盖，便于比对与重建。
- 注册结果写全局事件 `host.tasks_registered`，detail 是「已注册并写入定义：…」或「注册失败：…」。
- 预热没有对应的计划任务：预热由调度在 `preheat_minutes` 之前建运行完成；备份由每日 04:00 的计划任务执行，证据镜像由每周日 04:30 的计划任务执行，都允许唤醒计算机。

## 独立看门狗

看门狗是独立进程、独立任务，不依赖核心的任何代码路径；核心死了它也照常醒来。

- 心跳：核心每 60 s 原子写 `data\run\core.heartbeat`，内容 `{"pid":…,"started_at":…,"version":…,"last_tick":…,"active_run":…}`；写临时文件后 `MoveFileEx` 替换，避免读到半截。
- 检查：每 5 分钟一次。以下任一成立即判核心死亡——心跳文件不存在；心跳 `mtime` 距今超过 300 s；心跳里的 pid 不存活。
- 拉起：先核对 `data\run\core.lock` 与进程，确认死亡后执行 `schtasks /run /tn lap-backstop-core`。统一走计划任务，不直接 `CreateProcess`，保证启动参数与环境只有一处定义。
- 验收：拉起后 120 s 内必须出现新心跳，否则计一次失败。
- 停手：30 分钟滑动窗口内累计 3 次拉起验收失败即停止拉起，停手证据随标记落进 `data\run\watchdog.state.json`：窗口内失败次数、最近一次失败时刻、当时的心跳内容与核心日志尾部（最多 50 行、总计不超过 8 KiB）。事件 `host.watchdog_gave_up` 与通知由核心下一次成功启动取走补发，核心一直起不来时不会产生这条事件。事件 payload 的键是 `detail`、`failed_count`、`last_failure_at`、`heartbeat`、`log_tail`；状态文件缺失或损坏时无法证明发生过停手，同样不产生该事件。
- 记录：每次检查写一行 `data\logs\watchdog.jsonl`，字段 `at`、`heartbeat_age_s`、`core_pid`、`action`；dead-man 启用时随后追加它自己的结果行（`deadman.heartbeat`、`deadman.check_failed` 或 `deadman.error`）。
- 自约束：单次运行 3 s 内结束；dead-man 启用时心跳请求（上限 5 秒）与失败通知的网络等待不在此限，命名互斥量 `lap-backstop-watchdog` 保证同一时刻只有一个检查在跑。

采用「计划任务 + 短命进程」而非第二个常驻进程：看门狗自身崩溃或被结束不影响下一次检查，机器重启后由任务计划自动恢复。

## 单实例

| 机制 | 规则 |
|---|---|
| 互斥量 | 核心启动即取 `Global\lap-backstop-core`；取不到直接退出，退出码 3，写事件 `core.second_instance` |
| 锁文件 | `data\run\core.lock` 记 `pid`、`started_at`、`exe_path`、`boot_id`；pid 复用由 `started_at` 与 `boot_id` 排除 |
| 数据库 | SQLite WAL，一个写连接，`busy_timeout=5000`；绕过互斥量的进程也无法并发写 |
| 端口 | 默认监听 `127.0.0.1:8787`，地址与端口可配（`api.host`、`api.port`）；被非本实例占用时退出码 4，事件 `core.port_conflict` |
| 看门狗 | 单独的命名互斥量，重复触发直接退出码 0 |

## 磁盘与日志

| 可用空间 | 行为 |
|---|---|
| 低于 5 GB | 记 warn 日志与全局事件 `host.disk_low`，调度照常 |
| 低于 2 GB | 拒绝创建新 JobRun，运行中的继续跑完；事件 `host.disk_full_guard`，错误码 `E_DISK` |
| 低于 500 MB | 写事件 `host.disk_critical` 后退出码 5，留 500 MB 给日志收尾 |

- 全局事件只保留最近 1000 条：serve 循环在新一天的第一个 tick 清理一次，日期记在 settings 键 `maintenance.global_events_pruned_on`（见 [03](03-数据模型与接口.md)）；清理失败只记日志，不拖垮核心循环。
- 备份文件按份数修剪：日备 14 份、周备 8 份、配置导出 20 组，超出按最旧删除（`storage/db/backup.py`）。
- 保留清理每天本地 03:30 执行一次（时区取 `scheduler.timezone`）：证据文件 30 天且证据根总量不超过 20 GB（超限按最旧删终态运行的文件）、运行事件与阶段 30 天、判定与运行行 90 天、advisor_calls 90 天、原始日志 14 天、压缩日志 90 天；运行相关的删除只作用于终态运行，结果写全局事件 `core.retention_pruned`，失败只记日志并在下个 tick 重试（见 [03](03-数据模型与接口.md)）。
- 日志按 UTC 日界切分到 `data\logs\core-YYYY-MM-DD.jsonl`；单文件写满 200 MB 续号 `core-YYYY-MM-DD.2.jsonl`、`.3` 依次递增，一行不跨文件；进程内跨天在下一行写入前切换文件，不丢行；重启接当天最后一个未满文件继续追加。原始文件超过 14 天由保留清理删除。
- 超过 14 天的日文件压成同名 `.gz`：保留含今天在内 14 个 UTC 日期，压缩在进程启动与跨天时各做一次，失败只记日志；`.gz` 超过 90 天由保留清理删除。
- 看门狗日志是单个 `data\logs\watchdog.jsonl`，JSON Lines 追加写，不按天切分、不续号、不压缩、不清理。
- 每行是 `at`（UTC）、`level` 与调用方给的字段；`event` 缺省写 `unspecified`；不写 token、口令、截图内容。
- 日志只供排障，不作判定证据；证据走证据表与 `data\evidence\` 目录。

## 时钟与 NTP

- 调度按 `Schedule.timezone`（IANA 名）计算发生点，落库与事件一律 UTC。
- 启动校时：serve 启动时执行一次 `w32tm /resync`（单命令超时 10 秒），随后用 `w32tm /stripchart /dataonly /samples:1` 读本机墙钟与时间源的偏移。命令不存在、超时或非零退出都只落事件不阻断启动：结果记 `host.timesync_checked`（载荷 `detail`、`ok`）。偏移绝对值超过 `host.clock_skew_seconds`（默认 30 秒）时记 `host.clock_skew`（载荷 `detail`、`offset_seconds`，偏移为 stripchart 报告的带符号秒数）并把补跑暂停；偏移回到阈值内的下一次启动解除。偏移不可测时不下漂移结论，暂停状态保持原样。Windows Time 是否在运行仍由 `lap-backstop doctor` 第 12 项只读核对，不通过记 WARN。
- 补跑暂停的开关是 settings 键 `scheduler.catch_up_paused`（布尔）。暂停期间调度把已到点的发生点整段跳过，`next_run_at` 照常推进，不欠账；解除后从下一个发生点继续，暂停期间错过的发生点不补（见 [09](09-调度与作业语义.md) 错过与补跑）。
- 运行中检测休眠恢复：两次 tick 之间墙钟增量与单调增量之差即跳变量；绝对值超过 `host.clock_jump_seconds`（默认 120 秒）时记 `host.suspended`（载荷 `detail`、`jump_seconds`），全部环境置 unknown 并各探一次。进程内无论空闲还是执行运行，两个时钟同速前进，不会误报。
- 单调时钟用于进程内的时长判定：API 请求耗时、SSE 心跳间隔、插件调用与启动超时、心跳间隔；租约续租与过期、看门狗算心跳年龄都按墙钟 UTC 与文件 `mtime`。
- 单调时钟不跨进程：重启后超时与退避按数据库里持久化的 UTC 截止时间与下次尝试时间重建剩余量，已越过截止的按对应终态处置。

## 电源与唤醒

- 交流供电下关闭睡眠与休眠、允许关闭显示器：`lap-backstop doctor` 第 13 项只读核对 `powercfg` 的交流超时值，核心不改电源策略。
- 核心不检测交流与电池切换：电池供电时调度照常，不按电源种类拒绝新运行。
- 计划任务不带 WakeTimers，注册后不核对 `powercfg /waketimers`。
- 唤醒不单独触发环境动作：启动扫描对每个环境各 probe 一次，不复用启动前的 ready（见 [09](09-调度与作业语义.md) 崩溃恢复）。
- UPS 可选；断电后的恢复路径只有一条——重新登录并自动启动。

## 停机与阶段边界

- 信号与事件同源：核心注册 SIGINT、SIGBREAK、SIGTERM，处理器只置停机事件；`POST /api/v1/host/drain` 置同一个事件。两条路径走同一份停机收尾，日志与事件口径一致。
- 处理顺序：停机事件置位后，当轮 tick 不再推进任何一步——不查磁盘水位、不扫新运行、不接新作业；在途运行由执行器在阶段边界收尾；循环退出后依次关闭插件宿主、通知、API 与数据库，正常退出返回 0。
- 阶段行收尾口径：正在推进的运行停在阶段边界——当前阶段先跑完并写清阶段结论：执行中的脚本观察到自然结束，信号照常落库；到阶段截止或观察次数用尽则停脚本，与挂起的脚本一样落 timed_out。随后写 `run.interrupted`（载荷 `run_id`、`reason` 为 `shutdown`），不再开新阶段、不执行恢复动作。每个运行的停机收尾事件至多一条：重复收到停机信号不产生第二条 `run.interrupted`。
- 状态与租约：`run.interrupted` 不改运行状态、不动租约。下次启动扫描把准备中、执行中、验证中、清理中的运行置 `unknown` 并回收它们的孤儿租约，等待中的运行继续持有租约、重启后接着跑；清理已开始则不打断收尾，结论照落。
- 通知账目口径：正常停机把未投递的通知落成 `failed`（`error` 记「停机放弃投递」）；硬杀或断电走不到收尾，遗留的 `pending` 在下次启动、迁移完成后清扫为 `failed`（`error` 记「启动清扫：上次进程未正常退出」，`attempts` 保留、`sent_at` 留空），每条清扫落一条 `core.event`，单条清扫失败不阻断启动。
- 硬时限缺口：执行器在核心进程同步跑阶段（DEBT D-001），一次插件调用没有可强制打断的取消点，停机收尾只能等它返回，因此不做强制超时；卡死的阶段会让收尾一直等，升级排水按 3600 秒上限轮询核心退场、超时按升级失败中止（核心继续在跑，见升级与回滚）。强制超时依赖 D-001 执行器异步化。未执行的发生点按启动时的错过策略处理。

## Tailscale

- Tailscale 装为系统服务，随开机启动并加入 tailnet；关闭 Funnel，不开公网入口。
- 监听集合在启动时确定：默认只监听 `127.0.0.1`；settings 里 `api.remote_enabled` 为 true 时，启动阶段读 `tailscale status --json`，`BackendState` 为 Running 才把 tailnet IPv4（100.64.0.0/10）追加进监听集。非 Running 或不可查只写一次全局事件 `host.tailscale_down`（载荷 `{"event": "host.tailscale_down", "detail": <BackendState 或不可查原因>}`，同一进程生命周期只记一次，恢复 Running 后重启内核才生效）并走通知渠道；运行期不动态重绑。
- 回环成功而 tailnet 地址绑定失败时写 `host.tailscale_bind_failed`，继续只用已成功的监听地址；全部地址都起不来按端口被占退 4。
- 防火墙入站规则只放行回环与 tailnet 网段，由管理员手工执行一次；`api.port` 改过时 `localport` 同步改（规则名与 doctor 第 14 项对应）：

  ```bat
  netsh advfirewall firewall add rule name="lap-backstop-api" dir=in action=allow protocol=TCP localport=8787 remoteip=127.0.0.0/8,100.64.0.0/10
  ```

  核对：`netsh advfirewall firewall show rule name="lap-backstop-api"`；移除：`netsh advfirewall firewall delete rule name="lap-backstop-api"`。核心不自动改防火墙；doctor 第 14 项核对该规则存在且只放行回环与 tailnet，不通过给 WARN。
- 启动探测与 doctor 第 13 项共用同一解析口径（`core/hostops/tailscale.py`：`BackendState` 加 tailnet IPv4 提取），不出现两套判定。
- 手机端地址每次现算：在家用局域网地址，出门用 tailnet 地址，不缓存「在不在家」。
- 节点用 auth key 预授权加入，关闭密钥过期，避免无人值守期间掉线。
- Bearer token 只在请求头；不进日志、不进备份、不进事件字段。token 首次启动由内核自动生成（docs/03 鉴权与网络），撤销访问就是更换 token 并重启内核。

## 外部报警

dead-man 外部心跳：settings 键 `notify.heartbeat_url` 存外部 Push 服务地址（如 healthchecks.io 的 ping 地址），缺省空串表示不启用。启用后看门狗每轮检查通过即向该地址发一次 GET，超时上限 5 秒、默认关闭系统代理；外部监控在心跳停止超过其宽限期时告警——核心死、看门狗死、断电、断网、自动登录失败都会停发。

检查未通过时不发心跳，并立即按既有通知渠道（notify.*）发一条 fail；同一次失败事件只发一条，去重标记在 `watchdog.state.json` 的 `deadman_fail_notified`，检查恢复通过即清除，投递失败下一轮失败重试。通知正文只含动作、心跳年龄与核心 pid，不带心跳 URL。

- 未启用（空串）时不产生任何网络请求、不写任何日志，行为与没有该功能完全一致。
- 脱敏：URL 出现在日志里只保留来源（scheme://域名）与其后前 6 位，其余打码。
- 心跳与通知的任何异常只落 `watchdog.jsonl` 的结果行，不影响检查本身；配置随库而生，缺库按未启用静默处理，库损坏落 `deadman.error`。
- fail 通知与既有通知同路：机器断网时同样发不出去；持续失联只能靠外部监控发现。

## 备份与恢复

- 备份范围是数据库快照与平台配置导出：不包含 token 与密钥，证据目录 `data\evidence\` 不在每日备份内，由每周日的证据增量镜像单独搬进 `data\backups\evidence\`（见下节）。
- 备份由 `lap-backstop backup` 执行：`VACUUM INTO` 生成 `data\backups\db-YYYYMMDD-HHMMSS.sqlite`（在线一致快照，不锁写），同时导出 `settings.json` 与 `plugins.json`（插件 id、版本、启用状态），末尾按份数修剪。
- 每份快照写 `manifest.json`，含 SHA-256、行数、schema 版本；完成后跑 `PRAGMA integrity_check`，不通过则删除该份并发 ERROR 通知；快照生成失败同样发 ERROR 通知。
- 任何 schema 迁移执行前，强制再生成一份 `pre-migrate-<version>-<时间>.sqlite`；快照生成失败则不执行迁移，核心退出码 1。

### 证据增量镜像

- 频率：计划任务 `lap-backstop-evidence-mirror` 每周日 04:30 执行一次，允许唤醒计算机；入口 `lap-backstop evidence-mirror` 可随时手动执行。
- 增量规则：把 `data\evidence\` 搬进 `data\backups\evidence\`，按相对路径逐份比对——目标缺失或体积不同即搬运，体积相同再比 SHA-256，一致跳过；镜像只增不删，镜像里的旧文件不做清理。
- 体积裁剪：证据根总量超过 `backup.evidence_mirror_threshold_gb`（默认 20 GB）时，只搬 `verdicts.evidence_ids` 引用到的证据，其余文件留在证据根、不进镜像；未超过时整目录搬运。
- 失败与续做：每份文件先写临时名再原子替换，任一份搬运失败立即停止，事件 `host.evidence_mirror_failed` 记录失败原因，已落盘的都是完整文件，已有备份不受影响；重跑同一命令即续做，已一致的文件自动跳过。完成时写 `host.evidence_mirror_finished`，detail 含 copied_new、copied_changed、skipped_unchanged、skipped_by_policy、bytes_copied。

恢复顺序：

1. 停核心（API 停止或 `taskkill`），确认互斥量已释放。
2. 把现有库改名为 `backstop.corrupt-<时间>.sqlite`，保留现场。
3. 复制目标快照为 `data\backstop.sqlite`。
4. 执行 `lap-backstop db check`：`integrity_check` 加迁移到当前版本，失败即停并发 ERROR 通知。
5. 启动核心，核对 `/api/v1/health` 与最近 20 条事件。
6. 恢复 `settings.json` 与插件启用状态，触发一次环境 probe。

每月演练一次：在副本目录恢复并跑 [12](12-测试与质量门禁.md) 的冒烟集，记录耗时与失败点。

## 升级与回滚

- 布局：每个版本解压到 `app\releases\<version>\`，`app\current` 是指向它的目录联接；`scripts/build_app.py` 产出这一套（构建、平铺、重建联接）。
- 升级入口：`lap-backstop upgrade <新版本目录>`。新版本目录必须已在 `app\releases\<版本>\` 下且含 `lap-backstop.exe`；目标与当前版本相同则直接返回，不排水、不写事件。顺序固定为：drain → 升级前快照 → 切 `current` 联接 → 按计划任务启动 → 60 秒健康检查。启动只走计划任务 `lap-backstop-core`，与日常启动同一口径。
- drain 边界：核心在跑时经 `POST /api/v1/host/drain` 置位停机事件，与 SIGINT 同一路径——调度停止接新作业（到点的发生点保持待办，重启后按错过策略处置，不丢失也不欠账），在跑作业推进到阶段边界写 `run.interrupted` 后随进程退出，不被强杀；升级方轮询核心进程退场，上限 3600 秒。排水被拒或超时即中止升级：联接与库未动，核心继续在跑，服务照常。
- 快照位置：drain 后对平台库执行 `VACUUM INTO`，写 `data\backups\pre-upgrade-<版本>-<时间>.sqlite`，通过 integrity_check 才生效；不参与例行备份修剪，回滚后也不清理，去留由人工决定。
- 健康检查口径：拉起后 60 秒内 `GET /api/v1/health`（带访问令牌）返回 200 且 `status` 为 `ok`；每 2 秒探一次，只判服务就绪，不比对版本号。
- 回滚判定：计划任务启动失败或健康检查未通过即自动回滚——结束未就绪的新版本进程（就绪前执行循环未启动，没有在跑作业可损失）→ `current` 切回前一版本 → 现行库连同 WAL 改名为 `backstop.pre-rollback-<时间>.sqlite` 保留现场 → 复制 pre-upgrade 快照回 `data\backstop.sqlite` 并核对完整性 → 重新按计划任务拉起旧版本并做同样的 60 秒健康检查。只核对完整性、不再迁移：快照生成于前一版本在跑时，schema 就是前一版本期望的形态。
- 升级结果事件：成功写 `host.upgrade_finished`，失败写 `host.upgrade_failed`；载荷 `detail`、`ok`、`target_version`、`previous_version`，`ok` 表示服务是否恢复到旧版本并通过健康检查。回滚凭据记在 `data\run\upgrade.state.json`（目标版本、前一版本、快照文件名），升级成功或回滚完成即清除：标记存在表示一次升级尚无结论；`lap-backstop rollback` 按标记手动回滚，无标记即空操作——重复执行回滚与保留清理都不产生重复目录或重复事件。
- 版本保留：升级成功后 `app\releases\` 最多保留 3 个版本目录，超出按目录修改时间从最旧删除；当前版本与回滚目标（前一版本）永不删除，即使挤占保留名额。
- 迁移前的 `pre-migrate` 快照是迁移的前置保证（见上节），不负责版本切换。
- 数据库只前滚：迁移不删列、不删表；破坏性变更分两个版本完成（先加后用后删），保证前一版本仍能读当前库（[13](13-变更与演进.md)）。升级失败回滚因此必须连库一起回到快照。

## 排障顺序

| 现象 | 先看 | 常见原因 |
|---|---|---|
| 手机连不上 | 看门狗日志、任务状态 | 核心未运行、Tailscale 非 Running、端口被占 |
| 到点没跑 | 事件里的 schedule 与 catch_up | 错过策略为 skip、核心未运行、任务未注册 |
| 运行卡住 | 最后一条 run_event、心跳里的 active_run | 脚本挂起、环境未就绪、插件调用无超时 |
| 磁盘告警 | `data\evidence\` 与 `data\logs\` 体积 | 过期数据未人工清理、失败运行截图过多 |
| 重启后没恢复 | `host.autologon_checked` 事件 | 注册表被更新重置、账号口令过期、锁定屏幕 |
| 升级后反复重启 | 版本目录与迁移失败日志 | 迁移失败、插件 api_version 不兼容、端口冲突 |
