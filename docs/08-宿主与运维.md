# 08 · 宿主与运维

[返回总览](00-总览与索引.md)

本文回答：平台跑在什么 Windows 宿主上，机器重启、断电、断网、核心崩溃、版本升级时靠什么把服务拉回来。进程与模块见 [02](02-架构.md)，表与接口见 [03](03-数据模型与接口.md)，改动流程见 [13](13-变更与演进.md)。

## 宿主基线

| 项 | 要求 |
|---|---|
| 操作系统 | Windows 10/11 x64，开启硬件虚拟化 |
| 账号 | 专用本地账号 `backstop`，属 Administrators 组，只允许本机登录 |
| 会话 | 交互式登录会话；核心不由 Windows 服务托管 |
| Python | 3.12 及以上（宿主实测 3.14.3） |
| 模拟器 | MuMu 12 装在 `H:\MuMuPlayer`，实例 VM0 跑明日方舟（Android 15），adb `127.0.0.1:16384` |
| 外部脚本 | MAA 6.20.x 装在 `H:\MAA` |
| 显示 | 1280×720，缩放 100%；显示器可关，会话不得锁屏 |
| 电源 | 交流常供；电池只作短时兜底 |
| 网络 | 有线优先；Tailscale 提供外出访问地址 |

核心必须跑在交互式会话内。MuMu 是桌面 GUI 程序，服务所在的 Session 0 没有桌面合成与 GPU 上下文，窗口截图、点击、画面识别都不可用；核心、模拟器、游戏因此处于同一登录会话。

## 路径布局

| 用途 | 路径 |
|---|---|
| 版本目录 | `D:\lap-backstop\app\releases\<version>\` |
| 当前版本 | `D:\lap-backstop\app\current`（目录联接） |
| 数据库 | `D:\lap-backstop\data\backstop.sqlite` |
| 证据 | `D:\lap-backstop\data\evidence\` |
| 日志 | `D:\lap-backstop\data\logs\` |
| 备份 | `D:\lap-backstop\data\backups\` |
| 运行态 | `D:\lap-backstop\data\run\`（心跳、锁、pid） |
| 插件 | `D:\lap-backstop\plugins\<plugin_id>\` |
| 任务定义 | `D:\lap-backstop\data\host\tasks\*.xml` |

`data\` 与 `plugins\` 不随版本目录切换，升级不触碰运行数据。

## 自动登录

无人值守的起点是「重启后不需要有人按键」。自动登录没配好，整条恢复链路在第一步就断。

| 项 | 做法 |
|---|---|
| 注册表 | `HKLM\SOFTWARE\Microsoft\Windows NT\CurrentVersion\Winlogon`：`AutoAdminLogon=1`、`DefaultUserName=backstop`、`DefaultDomainName=<机器名>` |
| 口令 | 用 Sysinternals Autologon 写入 LSA secret；`DefaultPassword` 留空，不存明文 |
| 锁屏 | 关闭 Ctrl+Alt+Del 强制、屏保与动态锁；锁屏会让模拟器窗口不可交互 |
| 更新重启 | 关闭「更新后自动重启」的立即重启行为，更新安装时间避开调度窗口 |
| 自检 | 核心启动时读上述注册表值，写入事件 `host.autologon_checked`；值不为 1 或用户名为空时发一条 warn 通知 |
| 失败兜底 | 自动登录失败时机器停在登录界面，由外部心跳在 15 分钟内报警（见「外部心跳」） |

宿主当前 `AutoAdminLogon=0`、`DefaultUserName` 为空，上述自检会持续报警，直到注册表配置到位。

## 计划任务

四个任务，全部「仅在用户登录时运行」，触发器与动作固定，由核心在启动时按 settings 注册或修复。

| 任务名 | 触发器 | 动作 | 设置 |
|---|---|---|---|
| `lap-backstop-core` | 登录时，延迟 30 s | `app\current\lap-backstop.exe serve` | 失败后每 1 分钟重试，最多 3 次；不因运行超时停止 |
| `lap-backstop-watchdog` | 登录时，之后每 5 分钟 | `app\current\lap-backstop.exe watchdog check` | 单实例；不因运行超时停止 |
| `lap-backstop-preheat` | 预热前 `preheat_minutes` | `POST /api/v1/environments/{id}/prepare` | 允许唤醒计算机 |
| `lap-backstop-backup` | 每日 04:00 | `app\current\lap-backstop.exe backup` | 允许唤醒；失败不阻塞调度 |

- 「Stop the task if it runs longer than」一律不勾；核心是长驻进程。
- 「Start the task only if the computer is on AC power」关闭，否则电池时任务根本不启动。
- 实例策略用「Do not start a new instance」，与新实例排队冲突时以互斥量为准。
- 任务以 XML 导入，文件留在 `data\host\tasks\`，便于比对与重建。
- 界面提供「重新注册计划任务」按钮，注册结果写事件 `host.tasks_registered`。

## 独立看门狗

看门狗是独立进程、独立任务，不依赖核心的任何代码路径；核心死了它也照常醒来。

- 心跳：核心每 60 s 原子写 `data\run\core.heartbeat`，内容 `{"pid":…,"started_at":…,"version":…,"last_tick":…,"active_run":…}`；写临时文件后 `MoveFileEx` 替换，避免读到半截。
- 检查：每 5 分钟一次。以下任一成立即判核心死亡——心跳文件不存在；心跳 `mtime` 距今超过 300 s；心跳里的 pid 不存活。
- 拉起：先核对 `data\run\core.lock` 与进程，确认死亡后执行 `schtasks /run /tn lap-backstop-core`。统一走计划任务，不直接 `CreateProcess`，保证启动参数与环境只有一处定义。
- 验收：拉起后 120 s 内必须出现新心跳，否则计一次失败。
- 停手：30 分钟内连续 3 次拉起失败即停止拉起，发通知并写事件 `host.watchdog_gave_up`，附核心日志尾部与心跳内容，等人工处理。
- 记录：每次检查写一行 `data\logs\watchdog.jsonl`，字段 `at`、`heartbeat_age_s`、`core_pid`、`action`。
- 自约束：单次运行 3 s 内结束；命名互斥量 `lap-backstop-watchdog` 保证同一时刻只有一个检查在跑。
- 升级后自检：升级脚本切换 `current` 后由看门狗做第一次健康检查；健康检查失败即触发回滚（见「升级与回滚」）。

采用「计划任务 + 短命进程」而非第二个常驻进程：看门狗自身崩溃或被结束不影响下一次检查，机器重启后由任务计划自动恢复。

## 单实例

| 机制 | 规则 |
|---|---|
| 互斥量 | 核心启动即取 `Global\lap-backstop-core`；取不到直接退出，退出码 3，写事件 `core.second_instance` |
| 锁文件 | `data\run\core.lock` 记 `pid`、`started_at`、`exe_path`、`boot_id`；pid 复用由 `started_at` 与 `boot_id` 排除 |
| 数据库 | SQLite WAL，一个写连接，`busy_timeout=5000`；绕过互斥量的进程也无法并发写 |
| 端口 | 默认监听 `127.0.0.1:8787`，地址与端口可配（`api.host`、`api.port`）；被非本实例占用时退出码 4，事件 `core.port_conflict` |
| 界面外壳 | WebView2 外壳可重复启动；第二次启动只把已有窗口置前，不新建进程 |
| 看门狗 | 单独的命名互斥量，重复触发直接退出码 0 |

## 磁盘与日志轮转

| 可用空间 | 行为 |
|---|---|
| 低于 5 GB | 通知 warn，事件 `host.disk_low`，调度照常 |
| 低于 2 GB | 拒绝创建新 JobRun，运行中的继续跑完；事件 `host.disk_full_guard`，错误码 `E_DISK` |
| 低于 500 MB | 写事件后退出码 5，留 500 MB 给日志收尾 |

保留策略（双条件，先到先删，永远不动进行中的运行）：

| 数据 | 保留 |
|---|---|
| 证据 | 30 天（可配），总量不超过 20 GB |
| 运行记录、事件、阶段 | 30 天 |
| 判定（verdict） | 90 天 |
| 日志 | 14 天 |
| 数据库快照 | 14 份日备 + 8 份周备 |
| 配置备份 | 最近 20 份，见 [03](03-数据模型与接口.md) |
| advisor_calls | 90 天 |

- 清理作业每日 03:30 执行，按最旧优先删除；只删终态运行的证据；证据过期后删除文件、保留 verdict 并标注「已过保留期」。
- 日志为 JSON Lines，按天切分 `logs/core-YYYY-MM-DD.jsonl`；单文件超过 200 MB 追加序号续写，14 天后压成 `.gz`。
- 轮转在进程内完成，跨天不丢行；不删除正在写的文件（Windows 会拒绝）。
- 每行字段：`at`（UTC）、`level`、`event`、`run_id`、`plugin`、`fields`；不写 token、口令、截图内容。
- 日志只供排障，不作判定证据；证据走证据表与 `data\evidence\` 目录。

## 时钟与 NTP

- 调度按 `Schedule.timezone`（IANA 名）计算发生点，落库与事件一律 UTC。
- Windows Time 服务设为自动启动；核心启动时执行一次 `w32tm /resync`，失败只记 warn。
- 偏移超过 30 s 记事件 `host.clock_skew`；超过 5 min 暂停补跑与新预热并发通知，恢复同步后按 [09](09-调度与作业语义.md) 重新计算未执行发生点。
- 时长、超时、心跳间隔一律用单调时钟，不用墙钟相减，避免校时与休眠造成误判。
- 墙钟跳变超过 120 s 而单调时钟未同步增长，判定为休眠恢复：事件 `host.suspended`，所有环境置 `unknown` 并强制 probe。
- 单调时钟不跨进程：重启后超时与退避按数据库里持久化的 UTC 截止时间与下次尝试时间重建剩余量，已越过截止的按对应终态处置，并在事件里记录重建后的剩余量。

## 电源与唤醒

- 交流供电下禁止睡眠与休眠：`powercfg /change standby-timeout-ac 0`、`hibernate-timeout-ac 0`；允许关闭显示器。
- 电池供电下不创建新 JobRun，当前运行跑完再停；发通知；恢复交流后重新计算调度。
- 需要唤醒的运行由计划任务带 WakeTimers；注册后用 `powercfg /waketimers` 确认条目存在。
- 唤醒后 90 s 内环境一律视为 `unknown`，先 probe 再 prepare，不复用唤醒前的 `ready`。
- 关机与重启：核心处理会话结束与 SIGTERM，30 s 内停止创建新运行、释放租约，把进行中的运行交给启动扫描（见 [02](02-架构.md) 崩溃恢复），并写事件 `run.interrupted`；未执行的发生点由启动时的错过策略处理。
- UPS 可选；断电后的恢复路径只有一条——重新登录并自动启动。

## Tailscale

- Tailscale 装为系统服务，随开机启动并加入 tailnet；关闭 Funnel，不开公网入口。
- 默认只监听 `127.0.0.1`；开启远程后追加 tailnet 接口地址，不监听公网网卡、不做端口映射；防火墙入站规则限定回环与 `tailscale0` 接口上的配置端口。
- 启动时读 `tailscale status --json` 的 `BackendState` 与 `TailscaleIPs`；非 `Running` 时只提供本地访问，事件 `host.tailscale_down` 并通知。
- 手机端地址每次现算：在家用局域网地址，出门用 tailnet 地址，不缓存「在不在家」。
- 节点用 auth key 预授权加入，关闭密钥过期，避免无人值守期间掉线。
- Bearer token 只在请求头；不进日志、不进备份、不进事件字段。

## 外部心跳（dead-man）

本机彻底掉线时无法自报，报警必须来自机器之外。

| 项 | 规则 |
|---|---|
| 服务 | Healthchecks.io 或 Uptime Kuma 的 Push 监控，二选一 |
| 周期 | 300 s，服务端宽限 15 min |
| 发送者 | 看门狗，每次检查通过后 ping；核心不直接 ping |
| 成功条件 | `/api/v1/health` 正常、心跳 age 小于 120 s、本次检查未判定核心死亡 |
| 失败信号 | 任一条件不满足立即发 fail 并带一行原因，让外部服务马上报警，不等宽限 |
| 覆盖范围 | 核心死、看门狗死、断电、断网、自动登录失败都会停发 |
| 配置 | `notify.heartbeat_url` 存完整 URL；日志与事件里脱敏为域名加前 6 位 |

## 备份与恢复

- 备份内容：SQLite、证据目录、平台配置；不包含 token 与密钥。
- 每日 04:00 执行：`VACUUM INTO` 生成 `data\backups\db-YYYYMMDD-HHMMSS.sqlite`（在线一致快照，不锁写），同时导出 `settings.json` 与 `plugins.json`（插件 id、版本、启用状态）。
- 每周日 04:30 把证据目录增量镜像进备份目标；证据总量超过 20 GB 时只保留 verdict 引用到的证据。
- 每份快照写 `manifest.json`，含 SHA-256、行数、schema 版本；完成后跑 `PRAGMA integrity_check`，不通过则删除该份并发 ERROR 通知。
- 任何 schema 迁移执行前，强制再生成一份 `pre-migrate-<version>-<时间>.sqlite`。

恢复顺序：

1. 停核心（API 停止或 `taskkill`），确认互斥量已释放。
2. 把现有库改名为 `backstop.corrupt-<时间>.sqlite`，保留现场。
3. 复制目标快照为 `data\backstop.sqlite`。
4. 执行 `lap-backstop db check`：`integrity_check` 加迁移到当前版本，失败即停。
5. 启动核心，核对 `/api/v1/health` 与最近 20 条事件。
6. 恢复 `settings.json` 与插件启用状态，触发一次环境 probe。

每月演练一次：在副本目录恢复并跑 [12](12-测试与质量门禁.md) 的冒烟集，记录耗时与失败点。

## 升级与回滚

- 布局：每个版本解压到 `app\releases\<version>\`，`app\current` 是指向它的目录联接。升级即切换联接，不覆盖文件。
- 升级顺序：停止新建 JobRun（drain）→ 等当前运行结束（最长 30 min，超时按取消处理）→ 生成 pre-upgrade 快照 → 解压新版本并校验哈希与签名 → 执行迁移 → 切换 `current` → 启动并等 `/api/v1/health` 通过（60 s）→ 恢复调度。
- 自动回滚：health 未在 60 s 内通过，或启动连续失败 2 次，切回前一版本目录、用 pre-upgrade 快照恢复数据库、启动，发通知「升级失败已回滚」并附日志尾部。
- 数据库只前滚：迁移不删列、不删表；破坏性变更分两个版本完成（先加后用后删），保证前一版本仍能读当前库。
- 保留最近 3 个版本目录与对应快照，更旧的删除。
- 手工升级失败时 `current` 保持指向前一版本，删掉半解压目录，事件 `host.upgrade_failed`。

## 排障顺序

| 现象 | 先看 | 常见原因 |
|---|---|---|
| 手机连不上 | 看门狗日志、任务状态 | 核心未运行、Tailscale 非 Running、端口被占 |
| 到点没跑 | 事件里的 schedule 与 catch_up | 错过策略为 skip、时钟偏移超过阈值、任务未注册 |
| 运行卡住 | 最后一条 run_event、心跳里的 active_run | 脚本挂起、环境未就绪、插件调用无超时 |
| 磁盘告警 | `data\evidence\` 与 `data\logs\` 体积 | 保留策略未生效、失败运行截图过多 |
| 重启后没恢复 | `host.autologon_checked` 事件 | 注册表被更新重置、账号口令过期、锁定屏幕 |
| 升级后反复重启 | 版本目录与 `host.upgrade_failed` | 迁移失败、插件 api_version 不兼容、端口冲突 |
