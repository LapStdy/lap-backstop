# 05 · 更新模式

[返回总览](../00-总览与索引.md) · [返回方舟日常](00-方舟日常.md)

本文件回答：游戏更新为什么是独立作业、版本与公告从哪里读、维护时间窗怎么用、日常怎么让路与补跑、更新失败怎么处置、结论怎么判，以及它与 MAA 自身更新检测的关系。

## 作业类型

更新是独立 JobRun，不是 `prepare` 里的一个步骤。

| 项 | 取值 |
|---|---|
| 作业模板 | `arknights_update` |
| 插件 | MAA 插件（环境能力 + 脚本能力 + 验证能力） |
| 环境 | `arknights`，与日常共用同一租约 |
| 触发 | `at`（维护结束加缓冲）或探测到版本变化后的即时运行 |
| 优先级 | 90，高于日常的 10 |
| 截止时间 | 维护结束加 45 分钟 |
| 错过策略 | `skip`，合并 `coalesce=true` |
| 验证口径 | `dual`（版本 + 画面） |

版本探测本身不占环境：只发 HTTP 请求、写事件，不启动模拟器。只有确定要更新时才创建更新运行并申请环境租约。

## 数据源

| 源 | 地址 | 取什么 |
|---|---|---|
| 公告列表 | `https://ak.hypergryph.com/api/news?page=1&pageSize=20` | 标题、发布时间、`cid` |
| 公告正文 | `https://ak.hypergryph.com/news/<cid>` | 维护时间窗、更新类型、版本号 |
| 版本接口 | `https://ak-conf.hypergryph.com/config/prod/official/Android/version` | `clientVersion`、`resVersion` |

抓取规则：

- 白天每 6 小时拉一次列表，默认 06:00 到 22:00；正文按需拉取并缓存。
- 请求带浏览器 UA，走直连或平台配置的代理，不走系统代理。
- 单次超时 10 秒，失败重试 2 次；仍失败沿用上次结果并标 `stale`，不凭猜测断言。
- 每次抓取保存原文、`fetched_at`、HTTP 状态与内容哈希，作为公告解读的证据。

## 解析

| 字段 | 说明 | 示例 |
|---|---|---|
| `kind` | `maintenance`（停机维护）或 `flash`（闪断更新） | `maintenance` |
| `start` / `end` | 维护时间窗，`Asia/Shanghai` | `2026-09-20T16:00:00+08:00` |
| `client_version` | 客户端版本 | `2.5.00` |
| `res_version` | 资源版本 | 由版本接口给出 |
| `cid` | 公告编号 | `12345` |
| `fetched_at` | 抓取时间 | `2026-09-18T12:00:00+08:00` |

标题与正文的常见写法：

```text
[明日方舟]09月20日16:00闪断更新公告
计划将于 2026年09月20日16:00 ~ 16:10 期间进行服务器闪断更新
10月09日10:00-16:00停机维护
```

- 时间按 `Asia/Shanghai` 解析；正文只给日期与时间时补当年。
- 解析失败记 `parse_error` 并保留原文，不生成更新作业。
- `clientVersion` 变化表示客户端更新；`resVersion` 变化表示资源更新。两者都触发更新作业，判定条件不同。

## 触发与排期

| 条件 | 作业时间 | 说明 |
|---|---|---|
| 公告给出维护时间窗 | `end + 5 分钟` | 缓冲覆盖开服抖动 |
| 版本接口的 `clientVersion` 变化 | 发现后 1 分钟 | 没有公告时按版本变化走 |
| `resVersion` 变化且无客户端更新 | 下一次日常的 `prepare` 前 | 游戏内资源更新，不单独占一轮 |

- 幂等键：`schedule_id + scheduled_at`；同一维护窗与同一版本只允许一个更新运行。
- 多个公告指向同一维护窗时合并为一个作业，`scheduled_at` 取最早的结束时间加缓冲。
- 维护时间窗晚于当日 22:00 时，作业顺延到次日 06:00 后的第一个窗口。

## 让路与补跑

让路不引入新的调度字段，由资源租约与就绪门控实现：

1. 更新作业优先级更高，先拿到环境租约；日常作业在队列里等。
2. 日常到点时若维护未结束，`prepare` 看到维护或更新画面，状态停在 `booting`，按 probe 间隔重试，不点击。
3. 更新结束、环境回到 `ready` 后，日常继续 `prepare`；在 `window_minutes=120` 内完成补跑。
4. 日常已在 `execute` 时遇到维护开始，会收到 `游戏掉线，停止任务`；停止并释放租约，由更新作业接管，日常按恢复策略在窗口内重跑。
5. 超过 `deadline_minutes=180` 的日常记 `failed`，等下一个计划点，不强行插入。

- 更新成功不直接拉起日常；日常由自己的调度在补跑窗口内执行。
- 维护窗口内不反复重启模拟器；每次 probe 间隔 60 秒，写一条事件。

## 执行

| 顺序 | 步骤 | 判据 |
|---|---|---|
| 1 | 申请环境租约 | 租约到手才进入 `prepare` |
| 2 | 启动或复用 MuMu，拉起游戏 | 进程、窗口、adb、游戏进程通过 |
| 3 | 等登录并进入主界面 | 登录模板、主界面模板命中 |
| 4 | 进入更新界面 | 更新提示或下载进度画面命中 |
| 5 | 等待下载与安装 | 进度变化或画面变化；每 30 秒抽一帧 |
| 6 | 判定 | 版本达到目标，且主界面可进 |
| 7 | 收尾 | 按保温策略保留或关闭环境 |

- 更新界面只允许点击「更新」「下载」「确定」「继续」「关闭公告」；不点「清除缓存」「资源修复」「卸载」。
- 单次更新最长 45 分钟；连续 10 分钟无进度变化记 `stalled`，到上限停手。
- 游戏更新由客户端完成，平台只负责启动、等待、判定，不替换任何文件，不安装 APK。
- 更新期间不做日常抽帧以外的识别，不切后台、不改分辨率。

## 判定

| 来源 | `completed` | `failed` | `unknown` |
|---|---|---|---|
| 版本 | `clientVersion` 达到公告或接口给出的目标值 | 版本未变且出现更新失败画面 | 版本接口不可达 |
| 画面 | 主界面模板命中，无更新、维护、错误画面 | 命中更新失败、资源修复、网络错误画面 | 截图缺失、画面无法归类 |
| `dual` | 版本与画面都指向完成 | 任一来源明确失败 | 任一来源缺失或矛盾 |

- 「下载进度 100%」不是完成证据；必须看到版本变化或主界面可进。
- 闪断更新只要求维护结束后能进主界面，不要求 `clientVersion` 变化。
- 证据包含公告原文、版本接口响应、更新前后截图、版本号、总耗时。
- 版本接口不可达但主界面正常时记 `unknown`，通知里附截图，不记完成。

## 失败处置

| 情形 | 处置 |
|---|---|
| 公告抓不到 | 用版本接口兜底；仍失败按平时计划跑日常，事件标 `stale` |
| 维护未结束 | 等到结束加 5 分钟；超过截止时间记 `failed` |
| 下载卡住 | 到 45 分钟上限停手；窗口内允许重试 1 次 |
| 更新失败画面 | 停手通知，附截图；不点清除缓存或资源修复 |
| 更新后游戏异常 | 重启游戏 1 次；仍异常停手 |
| 版本接口与公告矛盾 | 以版本接口为准，公告原文保留；记冲突事件 |

## 与 MAA 自身更新检测的关系

- MAA 的 `Update` 检查的是 MAA 程序与 MaaResource，不是游戏客户端；两条更新线互不替代。
- MAA 在启动时检查更新，检测源当前是 MirrorChyan；检测到新版本会下载，是否自动安装由 `AutoInstallUpdatePackage` 控制。
- 安装由 `MAA.Updater.exe` 执行：等父进程退出、拿更新互斥、按计划文件替换程序与资源、按需重启。平台不碰这些文件。
- 日常作业运行中若 MAA 自更新并退出，日志没有完成行，按 `E_SCRIPT_EXITED` 处理：等更新结束、版本稳定后再重试一次。
- 作业模板固定 MAA 版本与资源版本；升级 MAA 走独立更新作业，升级后先跑冒烟作业，再恢复日常。
- `SkipStartupAutoRunAfterUpdate=true`：MAA 更新后重启时不自动开跑，避免更新重启链里插入一轮无人监督的任务。

## 安全

- 只访问官方公告与版本接口；游戏更新只走客户端自带通道，不使用第三方镜像。
- 不替换游戏文件、不安装 APK、不清除缓存、不做账号相关操作；公告原文、抓取时间、HTTP 状态与哈希留证；更新作业只在 06:00 到 22:00 执行。
