# 00 · 方舟日常

[返回总览](../00-总览与索引.md)

本文件回答：方舟环境由哪些部件组成、什么算就绪、日常作业跑什么、预热与保温怎么用、结果怎么验证、失败怎么恢复。

## 环境构成

| 部件 | 取值 |
|---|---|
| 模拟器 | MuMu 12，安装版本 6.5.4.0，目录 `H:/MuMuPlayer` |
| 实例 | index 0（VM0，名称「明日方舟」），系统 Android 15 |
| adb | `127.0.0.1:16384`，可执行文件 `H:/MuMuPlayer/nx_main/adb.exe` |
| 模拟器管理 | `H:/MuMuPlayer/nx_main/MuMuManager.exe` |
| 分辨率 | 1280×720，DPI 240 |
| MAA | 6.20.1，目录 `H:/MAA` |
| Python | 3.14.3 |
| 宿主 | Windows 10/11，交互式桌面会话 |
| 显示缩放 | 100% |

MuMu 是桌面 GUI 程序，必须运行在已登录的交互式会话里；Windows 服务的 Session 0 没有桌面，启动模拟器会失败。

## 环境状态

| 状态 | 判据 |
|---|---|
| `unknown` | 尚未 probe，或 probe 结果无法归类 |
| `off` | MuMu 进程不存在 |
| `booting` | 进程存在，虚拟机未启动完成，或 adb 未启动完成 |
| `ready` | 就绪判据全部通过，且没有脚本在执行（租约由资源层管理） |
| `busy` | 脚本执行中；租约在 prepare 前获取、cleanup 后释放 |
| `degraded` | 环境在运行，但游戏不在主界面、已掉线或画面无法归类 |
| `failed` | adb 失联、分辨率或缩放不符，probe 无法恢复 |

状态迁移只由 probe 与 prepare、reset、cleanup 动作触发，每次迁移写一条事件。`reset` 后回到 `booting`。

## 就绪判据

五项全部通过才算 `ready`；任一项失败按表中状态归类，不把「进程存在」当成就绪。

| 判据 | 探针 | 通过条件 | 失败归类 | 超时 |
|---|---|---|---|---|
| 进程 | `MuMuManager.exe info -v 0` | `is_process_started=true` 且 `player_state=start_finished` | `booting` / `failed` | 180 秒 |
| 窗口 | 上述 JSON 的 `main_wnd` | 句柄非 0，窗口可见、未最小化 | `booting` | 30 秒 |
| adb | `adb -s 127.0.0.1:16384 shell getprop sys.boot_completed` | 返回 `1`，且 `adb connect` 成功 | `failed` | 30 秒 |
| 游戏进程 | `adb -s 127.0.0.1:16384 shell pidof com.hypergryph.arknights` | 输出非空 | `booting` | 60 秒 |
| 模板 | 1280×720 截图，主界面 ROI `(700,530,930,720)` | 任一 `main_*` 模板得分 ≥ 0.85 | `degraded` | 300 秒 |
| 稳定帧 | 间隔 ≥ 300 毫秒的连续两帧 | 灰度哈希汉明距离 ≤ 2，或变化像素占比 ≤ 1% | `degraded`，继续等 | 3 秒 |

- 模板为多主题主界面模板集，任一命中即可。
- 稳定帧用来排除加载动画、转场和弹窗淡入；不稳定时继续截，不据此下结论。
- probe 结果附截图、模板名、得分、通道与耗时。

## 准备流程

| 顺序 | 步骤 | 命令或判据 | 超时 |
|---|---|---|---|
| 1 | 复用或启动 MuMu | 未运行则 `MuMuManager.exe control -v 0 launch` | 180 秒 |
| 2 | 校验分辨率与缩放 | 1280×720、缩放 100% | 10 秒 |
| 3 | 拉起游戏 | `adb shell monkey -p com.hypergryph.arknights -c android.intent.category.LAUNCHER 1` | 60 秒 |
| 4 | 等登录界面 | 登录模板命中 | 300 秒 |
| 5 | 点登录按钮 | 模板命中区域的中心；偏移超过 24 像素拒绝点击 | 30 秒 |
| 6 | 等主界面 | 任一主界面模板命中并稳定 | 300 秒 |

- adb 命令必须带 `-s 127.0.0.1:16384`：机器上可能存在 `emulator-5554` 残留，不带 `-s` 会报多设备。
- 登录点击只用固定安全坐标，坐标做区域钳制，点不进危险区域；识别不确定时不点。
- 准备阶段不启动 MAA。MAA 属于脚本，在 `execute` 阶段启动。

## 日常作业

日常作业的 MAA 任务集按执行顺序排列；任务集由作业模板保存，开跑前写入 MAA 配置，顺序即 MAA 的执行顺序。

| 顺序 | 任务名 | `$type` | 参数 |
|---|---|---|---|
| 1 | 开始唤醒 | `StartUpTask` | 无 |
| 2 | 刷理智 | `FightTask` | 关卡列表、理智阈值、吃药次数、次数上限 |
| 3 | 自动公招 | `RecruitTask` | 保留许可数、招募策略 |
| 4 | 基建换班 | `InfrastTask` | `RoomList`、`Filename` |
| 5 | 领取信用及购物 | `MallTask` | 购买项与优先级 |
| 6 | 领取奖励 | `AwardTask` | 无 |

- 任务项最少写 `$type`、`Name`、`IsEnable`，其余字段由 MAA 按默认值补全。
- `StagePlan`、`RoomList` 是列表，必须写 JSON 数组；类型写错会让整份配置解析失败。
- 作业只统计 `IsEnable=true` 的任务；禁用的任务不参与任务集判据。

## 时间与参数

| 项 | 取值 |
|---|---|
| 触发 | `cron: 0 3,15 * * *`，时区 `Asia/Shanghai` |
| 错过策略 | `catch_up=run_once` |
| 补跑窗口 | `window_minutes=120` |
| 截止时间 | `deadline_minutes=180` |
| 预热 | `preheat_minutes=30` |
| 保温 | `keep_warm_minutes=240` |
| 抽帧间隔 | 30 秒 |
| 验证口径 | `dual`（脚本 + 画面） |

调度字段语义见 [09-调度与作业语义](../09-调度与作业语义.md)，作业模板与插件契约见 [plugins/maa](../plugins/maa.md)。

## 预热与保温

预热：

1. 02:30 创建 JobRun，进入 `prepare`；
2. 启动或复用 MuMu，拉起游戏，完成登录，等到主界面稳定；
3. 环境 `ready` 后进入 `waiting`，到 03:00 进入 `execute`。

实测冷启动约 55 秒，游戏启动与登录在慢机器上按分钟计；预热把这段移出关键路径。MAA 不属于环境，MAA 启动到资源加载完成约 72 秒仍计入 `execute`。

保温：

- `keep_warm_minutes` 内保持 MuMu 与游戏 `ready`，03:00 与 15:00 两轮之间不冷启动；
- MAA 每次运行独立启动，完成后按 `PostActions=ExitSelf` 退出；游戏与模拟器由 `cleanup` 在保温结束时关闭，不由 MAA 关闭；
- 超过保温窗口、用户停手、维护或更新开始时立即 `cleanup`；
- 保温期间环境保持 `ready`、不持有租约、不占执行 worker；后续作业可重新申请租约。

## 执行与观测

- `execute` 启动 MAA，工作目录 `H:/MAA`，不带参数；`RunDirectly=true` 时 MAA 自动开跑。
- 观测以 `gui.log` 为主，`asst.log` 补充任务链与理智采样；日志信号与配置见 [02-MAA操作与配置](02-MAA操作与配置.md)。
- 运行期间每 30 秒抽一帧，只读，不注入点击；抽帧用于卡住判定与画面证据。
- 单轮结束后先 `verify`，再 `cleanup`，最后写通知。

## 验证

验证由 MAA 插件的 Verifier 执行，默认 `dual`。任务集、理智、结束画面三类证据：

| 证据 | 判据 | 缺失时 |
|---|---|---|
| 任务集 | 每个启用任务都有 `完成任务: X`，且 `任务已全部完成！` 出现，无 `任务出错: X` | 记 `unknown` |
| 理智 | `SubTaskExtraInfo` 的 `SanityBeforeStage.current_sanity` 在刷理智前后各采一次，运行后低于运行前 | 记证据缺失，`unknown` |
| 结束画面 | 主界面模板命中，且无错误框、掉线、维护、更新画面 | 记证据缺失，`unknown` |

`asst.log` 的 `AllTasksCompleted` 不能作为完成依据：整轮任务全部出错时它同样会触发。

| 口径 | `completed` | `failed` | `unknown` |
|---|---|---|---|
| `script` | 完成行出现，无错误行，MAA 正常退出 | 任务出错或掉线 | 完成行缺失、日志截断 |
| `screen` | 结束画面为主界面，无异常画面 | 命中错误框、掉线、维护或更新画面 | 截图缺失、画面无法归类 |
| `dual` | 脚本与画面都指向完成 | 任一来源明确失败 | 任一来源缺失或两者矛盾 |

结论只取 `completed`、`failed`、`unknown`，不把证据缺失降级为完成。

## 恢复

| 故障 | 信号 | 动作 | 上限 |
|---|---|---|---|
| adb 失联 | `adb connect` 失败 | `adb disconnect` 后重连；仍失败重启 MuMu | 1 次/attempt |
| 模拟器起不来 | 180 秒未 `start_finished` | 再 `launch` 一次 | 1 次/attempt |
| 游戏起不来 | 60 秒无游戏进程 | 再拉起一次；仍失败重启 MuMu | 1 次/attempt |
| 等不到登录 | 300 秒无登录模板 | 重启游戏一次 | 1 次/attempt |
| 等不到主界面 | 300 秒无主界面模板 | 重试点击登录两次；仍失败重启游戏 | 2 次/attempt |
| 开始唤醒超时 | `任务出错: 开始唤醒`，实测 66 秒 | 重启游戏，等到主界面后重跑；连续 2 次停手 | 2 次/attempt |
| 掉线 | `游戏掉线，停止任务` | 复位环境后重试 | 1 次/attempt |
| 任务出错 | `任务出错: X` 或 `任务已结束，以下任务出现错误:` | 重启 MAA，整条队列重跑一次 | 1 次/attempt |
| 维护或更新中 | 维护、更新界面模板 | 等到维护结束加 5 分钟缓冲；当天日常按补跑处理 | 到 `deadline` |
| 分辨率或缩放不符 | 校验失败 | 停手并通知，不改系统设置 | 终态 |
| 证据缺失 | 截图不可读或模板连续失配 | 记 `unknown`，通知，不重试 | 终态 |

恢复动作由内核按恢复策略路由，插件只执行并返回结果；动作本身不产生结论。

29 天统计：开跑 60 次，完成 44 次，掉线 8 次，3 轮任务出错。掉线与唤醒超时是两条主要恢复路径。

## 边界

- 不修改游戏客户端文件，不注入、不破解、不做游戏内作弊。
- 不修改 MAA 程序文件，只读写 `H:/MAA/config` 与 `H:/MAA/debug`。
- 一台机器同一时刻只允许一个方舟作业占用环境；第二个作业排队，不启动第二个实例。
- 点击只走白名单动作，危险区域在代码里显式排除；识别与动作规则见 [01-识别与动作](01-识别与动作.md)。
