# 09 · 调度与作业语义

[返回总览](00-总览与索引.md)

## 这份文件回答什么

一个作业在什么时刻、什么条件下执行；重复触发如何避免；错过、并发、超时、预热、保温、恢复分别怎么算。状态机定义见 [02](02-架构.md)，租约表结构见 [03](03-数据模型与接口.md)。

## 调度类型

| 类型 | 字段 | 例子 |
|---|---|---|
| cron | expr、timezone | 0 3,15 * * * |
| at | at（RFC3339） | 2026-10-24T03:00:00+08:00 |
| interval | every_minutes | 每 360 分钟 |

公共字段：

| 字段 | 含义 | 默认 |
|---|---|---|
| timezone | IANA 时区 | Asia/Shanghai |
| catch_up | 错过策略：run_once / skip / window | run_once |
| window_minutes | 补跑窗口 | 120 |
| coalesce | 多个错过点合并为一次 | true |
| priority | 队列优先级，数值越大越优先 | 0 |
| deadline_minutes | 从计划时间起的截止时间 | 180 |
| preheat_minutes | 提前进入 prepare 的分钟数 | 0 |
| keep_warm_minutes | 运行结束后保持环境就绪的分钟数 | 0 |
| enabled | 是否启用 | true |

配置校验：`window_minutes <= deadline_minutes`；违反时拒绝保存并返回 `E_CONFIG`。这样补跑窗口内产生的运行不会因为截止时间更短而必然失败。

## 幂等

- 幂等键：`<schedule_id>:<scheduled_at>`，scheduled_at 取 UTC 并截断到整秒；`at` 带小数秒时同样先截断。
- job_runs 对幂等键建唯一约束；补跑、双击、崩溃恢复、重试都复用同一个 JobRun。
- attempt 是 JobRun 内的尝试序号，不产生新的幂等键。
- 手动立即跑使用请求头的 Idempotency-Key 派生幂等键：`manual:<Idempotency-Key>`；缺该头返回 `E_BAD_REQUEST`，同一键重复提交返回同一个 JobRun。请求键与运行的对应关系存 [03](03-数据模型与接口.md) 的 `request_idempotency` 表。

## 错过与补跑

启动时计算每个启用调度在停机期间的发生点：

| 策略 | 行为 |
|---|---|
| run_once | 只补最近一个发生点；更早的放弃 |
| skip | 不补，直接排下一次 |
| window | 发生在 window_minutes 内的补跑；窗口外放弃 |

合并（coalesce=true）时，多个错过点只生成一个 JobRun，scheduled_at 取最近一个发生点，被合并的其它发生点写进 `run.created` 事件的 `merged_scheduled_ats`。

补跑暂停：启动校时测得墙钟偏移超阈值时（settings 键 `scheduler.catch_up_paused`，见 [08](08-宿主与运维.md) 时钟与 NTP），时钟不可信，暂停期间所有调度把已到点的发生点整段跳过，`next_run_at` 照常推进；解除后从下一个发生点继续，暂停期间错过的发生点不补，不欠账。

## 队列与截止时间

- 队列按 priority 降序、scheduled_at 升序、created_at 升序出队；不使用入队时间做排序。
- 同一环境同一时刻只有一个作业持有租约；其余排队。
- 截止时间 = scheduled_at + deadline_minutes。超过截止时间仍未进入 executing 的运行记 failed，错误码 `E_DEADLINE`，发通知；该发生点不再补跑，其它错过点仍按 catch_up 的规则处理。
- 截止时间不是取消：用户取消与系统截止是两种终态原因，分别写 cancelled 与 failed。
- 手动运行可插队，但不得抢占已持有租约的作业。

## 预热与保温

### 预热

preheat_minutes > 0 时：

1. 在 scheduled_at - preheat_minutes 创建 JobRun，入队后进入 prepare；
2. prepare 完成、环境 ready 后进入 waiting，租约持有到执行结束；
3. 到 scheduled_at 进入 executing。

预热把冷启动移出关键路径。慢机器上，preheat_minutes 按最近冷启动耗时的 P95 加缓冲计算，最少 10 分钟。

### 保温

keep_warm_minutes > 0 时：

- cleanup 不关闭环境，释放租约，Environment 回到 ready；
- 环境记录 warm_until = cleanup 时间 + keep_warm_minutes；
- 保温期间不持有租约、不占用 worker、不续租；任何后续作业可以重新申请租约；
- 超过 warm_until 无作业，由核心的保温清理任务关闭环境，环境回到 off；
- 显式停手、维护、更新、用户关闭应用时立即清理。

保温与预热的组合：两次触发之间的间隔小于保温窗口时不重复冷启动；间隔超过窗口时，由下一次运行的预热在 scheduled_at - preheat_minutes 重新启动环境。

## 资源租约

- 资源类型：environment、account、gpu、custom。
- environment 类型容量固定为 1：同一环境同一时刻只有一个租约、一个执行者。
- 其它资源可声明 capacity > 1；容量大于 1 时允许多个租约，但每个租约仍绑定一个 run。
- 获取顺序：按资源 id 排序，避免死锁；全部获取后才进入 prepare。
- 租约在 prepare 前获取，一直持有到 cleanup 完成；预热的 prepare 与 waiting 期间持有租约，保温期间不持有。
- 每次执行尝试的 provider cleanup 至多调用一次：进入 cleaning 的尝试由清理阶段调用，未进入 cleaning 的失败与取消收尾各调用一次；恢复重试是新执行尝试，下一次尝试重新清理。
- 续租：活动运行由核心的租约管理器每 60 秒续租，不依赖 worker 存活；TTL 默认 10 分钟。
- 过期：核心回收租约并写事件。若本次 attempt 仍有预算，运行进入 recovering，最早 60 秒后重新申请租约；排队中的运行先按出队顺序执行。租约仍被占用时运行继续排队，拿到后进入 prepare；超过截止时间仍未进入 executing 的按 `E_DEADLINE` 记 failed。预算耗尽的记 failed，错误码 `E_RESOURCE_LEASE_LOST`。

## 尝试与恢复

- 每次失败生成 recovery 决策：retry、reset_environment、restart_script、abort。
- retry 采用指数退避：30 秒、2 分钟、5 分钟；上限由作业模板配置。
- reset_environment 调用 EnvironmentProvider.reset；restart_script 调用 ScriptAdapter.recover。
- 达到预算进入 failed，发通知，附最后证据。
- 恢复动作本身失败按更高一级处理，不得无限循环。
- 恢复决策与结果写入事件；每次 attempt 独立编号。

## 取消与停止

- 取消请求写入 run_events；在阶段边界生效。
- 排队运行在出队窗口内（执行器已读出 queued、尚未迁移 preparing）被叫停：叫停赢，执行器退让，以 cancelled 收尾，不进入 preparing，也不留下活跃租约。
- executing 阶段取消：先 script.stop(graceful)，等待超时后 force；之后进入 cleaning。
- cleaning 阶段取消：等 cleanup 完成，再记 cancelled。
- 取消不记为失败；记为 cancelled，并记录原因。
- 用户停手（stop all）取消所有排队与运行中的作业；运行中的先 stop 脚本，再清理并释放租约。

## 崩溃恢复

启动时：

1. 扫描 scheduled、queued、preparing、waiting、executing、verifying、cleaning、recovering 的 JobRun；
2. 按最后事件重建阶段与 attempt；
3. 能续跑则重新入队；不能续跑则标记 unknown，或按恢复预算记 failed，并发通知；
4. 清理孤儿租约与临时文件；
5. 对每个环境各 probe 一次，不复用启动前的 ready；状态不明时进入 unknown 并等待下一次 probe。

核心崩溃不丢调度：next_run 持久化在数据库；启动后立即计算错过点。

## 时区与时钟

- 数据库存 UTC；展示按用户时区。
- cron 计算使用 IANA 时区；夏令时不存在的时间点跳过，重复的时间点只执行一次。
- 超时与退避按注入时钟的 UTC 时间判定；单调时钟只用于进程内时长，时钟来源与同步现状见 [08](08-宿主与运维.md) 的时钟一节。
- 重启后单调时钟不跨进程：超时与退避按持久化的 UTC 截止时间重建剩余量，已越过截止的按对应终态处置。

## 示例

~~~yaml
id: arknights_daily
kind: cron
expr: "0 3,15 * * *"
timezone: Asia/Shanghai
catch_up: run_once
window_minutes: 120
coalesce: true
priority: 10
deadline_minutes: 180
preheat_minutes: 30
keep_warm_minutes: 240
job_template_id: maa_arknights_daily
enabled: true
~~~

行为：02:30 创建运行、获取租约并进入 prepare；环境 ready 后 waiting；03:00 进入 executing；03:40 完成 cleanup、释放租约，环境保持 ready 到 07:40；到 15:00 这一班由 14:30 的预热重新启动环境，15:00 进入 executing；若 03:00 时仍未就绪，等待到 06:00 的截止时间，期间持续 probe 与恢复。
