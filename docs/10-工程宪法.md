# 10 · 工程宪法

[返回总览](00-总览与索引.md)

## 这份文件为什么存在

项目越做越难改，通常不是技术难题，而是规矩慢慢失守：为了赶进度绕一下、为了省事复制一段、为了不改旧代码多写一个分支。每一次都合理，合起来就把项目压垮。

这份文件把「什么不能做」和「怎么证明做对了」固定下来。能用机器检查的交给门禁（[12](12-测试与质量门禁.md)）；不能机器检查的交给评审清单（[13](13-变更与演进.md)）。

## 十条不可妥协

1. **内核不依赖具体脚本与游戏。** 插件的启动方式、日志格式、配置结构、判定口径不得进入内核；违反由依赖检查与契约测试拦下。
2. **配置是数据，执行是插件代码。** 用户可编辑的时间、参数、策略是数据，由插件 schema 定义；执行逻辑写在插件里，不塞进通用步骤 DSL。
3. **平台数据库是唯一真源。** 外部系统的配置通过插件 config projection 同步；差异由插件声明处理策略，内核只记录 revision 与结果。
4. **结论有证据，动作有事件。** 每条 Verdict 附可复核证据；每个阶段、动作、恢复都有事件；没有证据的结论不算结论。
5. **修 bug 先写失败用例。** 先让它红，再让它绿；没有用例的修复，下次还会坏。
6. **门禁不过不算完成。** 完成由工具判定，不由感觉判定。
7. **小步前进，契约先行。** 内核与插件接口先写 ADR 与契约测试，再写实现；一次改动只做一件事。
8. **绕行有到期日。** 任何临时绕行都要进 DEBT.md，写清原因、影响与归还期限。
9. **文档同改。** 改接口、改结构、改流程，同一次改动里把对应文档改掉；文档与代码不一致时，文档算错。
10. **不确定就问。** 需求不清、影响面不清、代价不清时停下来问，不猜着写。

## 腐化模式对照表

| 症状 | 根因 | 对应规矩 |
|---|---|---|
| 加一个脚本要改内核 | 内核耦合具体脚本 | 1、[11](11-代码规约.md) |
| 平台变成某款游戏专用 | 判定/配置/任务模型进了内核 | 1、2 |
| 配置文件与平台状态互相打架 | 多个真源 | 3 |
| 线上问题查不到原因 | 没有事件与证据 | 4 |
| 补丁越积越多 | 绕行没有期限 | 8 |
| 文档没人信 | 文档与代码脱节 | 9 |
| 不敢重构 | 没有测试兜底 | 5、[12](12-测试与质量门禁.md) |
| 抽象越做越重 | 没有第二个真实插件就抽通用层 | 7、[ADR 0005](adr/0005-契约先行与双插件验证.md) |
| 每个人写法不同 | 没有统一规约 | [11](11-代码规约.md) |
| 半成品混进主线 | 完成定义缺失 | [13](13-变更与演进.md) |

## 违反时怎么办

| 情形 | 做法 |
|---|---|
| 需求或影响面不清 | 停下来说明缺什么，等人回答；不猜 |
| 必须破例 | 记进 DEBT.md：为什么破、影响是什么、何时归还 |
| 觉得规矩本身不对 | 提 ADR 说明冲突与替代方案，人确认后修改本文 |
| 发现别人或 AI 违反 | 先把这一处修正，再继续；不「下不为例」 |

## 谁受约束

人、AI、脚本一视同仁。AI 产出的代码同样过全部门禁与评审清单，不因为「看起来对」而豁免。

## 修改本文

- 增加一条：说明它挡住哪个已发生的具体问题。
- 删除一条：说明为什么不再需要，并确认不会让老问题回来。
- 修改走 ADR，人确认后生效。
